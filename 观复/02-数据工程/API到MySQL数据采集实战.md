# API 到 MySQL 数据采集实战

> **先修**：[[Python环境与依赖]]、[[Python模块导入与包管理]]、[[SQL与MySQL基础]]。这里记录一条领星 FBA V2 库存接口到 MySQL ODS 的历史项目链路；签名字段、接口状态码和表结构应以当前项目与供应商文档重新核对。
> **核验状态**：未核验——来自已结束的历史项目，签名字段、接口状态码与表结构须按当前项目与供应商文档重新核对。详见 [[知识库质量审计]]。

## 这份案例解决什么

目标是在确定的采集批次内，取全库存记录、保留来源与时间，并能回答：**拉了多少、写了多少、失败在哪里、重跑会不会重复？** 通用 Python 语法不在这里重复讲；故障定位方法见 [[调试与排错方法]]。

```text
领星库存 API → 鉴权与分页 → 响应校验 → 字段转换 → MySQL ODS 快照
                         ↘ 批次记录 / 错误记录 / 数量对账 ↗
```

## 一、先定义输出，再写请求

一条 ODS 记录至少需要源系统业务键、必要原字段、采集批次或 `sync_time`，并明确一行代表“某店铺 × 某 SKU × 某仓库 × 某次采集”还是其他粒度。`sync_time` 是**采集时间**，不等于源系统的业务更新时间。分层职责见 [[数据仓库分层：从 ODS、DWD、DWS 到湖仓一体]]。

开始前检查三类契约：

| 契约 | 必须回答 |
| --- | --- |
| 接口 | 鉴权方式、签名字段与字节序、每页大小、排序、限流、业务成功码、错误码 |
| 数据 | 响应对象或数组的位置、业务键、空值、金额与整数的表示、嵌套字段 |
| 落库 | 表粒度、列类型、唯一性、批次重跑策略、事务范围、失败后如何恢复 |

历史项目以 `uv run v1` 启动，配置来自项目 `.env`，Token 有本地缓存。具体项目结构与解释器问题见 [[Python环境与依赖]]、[[Python模块导入与包管理]]；密钥不应写进笔记或代码库。

## 二、请求：分清传输成功与业务成功

一次请求有 URL、方法、Query、Body、Header 和超时。HTTP 200 只说明传输层收到正常响应，还要按接口文档检查 JSON 中的业务状态。历史记录中曾出现 `code=2001006`，但单凭这个数字不能推定原因；排查应保存脱敏后的请求 ID、参数摘要和响应消息。

历史签名流程涉及参数排序、稳定序列化、摘要及后续编码。任何一个空值规则、字段顺序、JSON 空格或字符编码差异都可能使结果不同。签名代码应只保留一份，并用供应商给定的固定输入／固定输出向量验证；本文不把旧实现当成当前接口规范。

## 三、分页：防漏、重与无限循环

```python
rows = []
offset = 0
while True:
    page = fetch_page(offset=offset, length=page_size)
    if not page:
        break
    rows.extend(page)
    offset += len(page)
    if len(page) < page_size:
        break
```

这只是接口采用 `offset`/`length` 且**短页表示结束**时的最小模型。若接口提供可信 `total`、游标或稳定排序，应按其契约调整。分页期间源数据变化可能导致重漏；生产同步需考虑时间窗口、快照令牌或去重，并记录每页偏移、行数和请求状态。失败后重试同一页，不应直接跳到下一页。

## 四、转换与写库：保证粒度不变

JSON 对象和数组在 Python 中分别常对应 `dict` 与 `list`；解析后先验证结构再取字段。金额用十进制语义处理，整数列只接受业务上确认为整数的值；不要把 `int(float(value))` 当作通用清洗规则，它可能截断小数，也可能丢失大整数精度。嵌套字段若写入 JSON 列，需明确序列化与空值规则。

数据库写入使用参数化语句，保证**列名数 = 占位符数 = 每行值数**。`CREATE TABLE IF NOT EXISTS` 只在表不存在时建表，不会把旧表升级到新结构；历史项目曾因缺少 `raw_data` 列报错，须核对真实表结构并显式迁移。

每批生成一个 `batch_id` 或固定 `sync_time`，以它标识该次采集。把“写入成功”“批次完成”放在同一个可解释的事务或状态流程中；失败时回滚并留下可重试记录。仅用当前时间追加快照而不设重跑策略，会在人工重跑后产生重复批次。

## 六、最小验收与后续改进

1. 记录源接口总数、逐页行数、去重后行数、数据库写入数；差异必须能解释。
2. 抽取一个小批次，核对业务键、空值、金额、时区与 `sync_time`。
3. 对相同批次重跑，确认不会产生重复快照；中途故障后确认能从明确位置恢复。
4. 用真实错误响应验证超时、鉴权失败、业务失败、限流与表结构变化。
5. 日志记录批次、请求 ID 和错误类型，隐藏 Token、密钥与个人数据。

目前这篇是**项目经验重构**，不是对现行领星 API 或 MySQL 实例的运行验收。未来真正重跑时，优先补齐幂等键、批次日志、对账和失败恢复；验证结果再写入 [[知识库质量审计]]。
