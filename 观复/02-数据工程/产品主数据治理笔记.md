# 产品主数据治理笔记

> **先修**：[[数据治理建设笔记]] 与 [[数据认知框架]]。
> **核验状态**：未核验——治理思路为整理时撰写，尚无来源标注与可复现的记录。详见 [[知识库质量审计]]。

这篇笔记以电商企业为背景，解释产品族、SPU、SKU、Listing 和组合产品之间的关系，并给出产品主数据从混乱走向可管理的完整思路。

## 背景：为什么产品名称越多，企业反而越难认识产品

同一款理疗仪可能同时拥有：

- 研发型号：C01J；
- ERP 料号：10002345；
- 内部 SKU：NC-C01J-BLK-US；
- Amazon Seller SKU：C01J-US-BLACK-FBA；
- Amazon ASIN：B0XXXXXX；
- 财务名称：Nicwell 理疗仪美国版；
- 仓库简称：C01J 黑美；
- 运营活动名：Prime Day 主推款。

这些名称都可能有用，但它们服务不同场景。
如果企业没有稳定的产品身份和映射关系，就会出现：

- 不知道多个名称是否指向同一产品；
- 库存、销售和成本无法对齐；
- 产品改名后历史数据断裂；
- 组合产品的库存和成本被错误计算；
- 一个 Listing 更换 SKU 后，历史订单被归错；
- 报表只能依赖模糊的文本匹配。

产品主数据治理的目标，是建立一张稳定的“产品身份证系统”。

可以把产品名称看作人的昵称，SKU 看作某个具体库存单位的身份证号码，Listing 则像这个人在某个平台开的店铺页面。
昵称可以变化，页面可以更换，但内部必须知道它们对应谁。

## 先区分五个核心对象

~~~mermaid
flowchart TD
    PF[产品族 Product Family] --> S1[SPU C01J]
    PF --> S2[SPU C02J]
    S1 --> K1[SKU 黑色美国版]
    S1 --> K2[SKU 白色美国版]
    S1 --> K3[SKU 黑色英国版]
    K1 --> M1[SKU-Listing 映射]
    K2 --> M1
    M1 --> L1[Amazon US Listing]
~~~

### 产品族

产品族表示用途、技术路线或市场定位相近的一组产品。

例如：

~~~text
TENS 理疗系列
├── C01J
├── C02J
└── C03J
~~~

产品族适合回答：

- 哪条产品线增长最快；
- 某系列总体毛利如何；
- 是否应该继续投入这一类产品。

产品族的边界由企业的管理目的决定，不是自然界唯一正确的分类。

### SPU

SPU 通常表示一个标准化产品概念，不区分某些库存或销售差异。

例如 C01J 理疗仪可以作为一个 SPU，其不同颜色、市场插头和包装版本形成多个 SKU。

SPU 适合回答：

- C01J 整体销量多少；
- C01J 与 C02J 的表现如何；
- 一个标准产品在不同市场的差异是什么。

企业必须明确哪些属性变化会产生新 SPU。
颜色通常可能只产生新 SKU，核心功能或型号变化则可能需要新 SPU。

### SKU

SKU 是 Stock Keeping Unit，即库存管理单位。

只要某项差异需要独立采购、储存、计价或发货，通常就需要独立 SKU。

例如：

| SKU | 颜色 | 市场 | 插头 | 包装 |
| --- | --- | --- | --- | --- |
| NC-C01J-BLK-US | 黑色 | 美国 | US | 英文 |
| NC-C01J-WHT-US | 白色 | 美国 | US | 英文 |
| NC-C01J-BLK-UK | 黑色 | 英国 | UK | 英文 |

SKU 回答的是“仓库里具体是哪一种货”。

### Listing

Listing 是特定平台、站点和店铺中的销售载体。

它可能包含：

- 平台；
- 站点；
- 店铺；
- ASIN 或平台商品 ID；
- 页面标题；
- 销售状态；
- 上下架时间。

Listing 不是产品本体。
同一产品可以有多个 Listing，一个 Listing 也可能销售多个 SKU，例如父子变体或套装。

### 平台

平台是 Amazon、TikTok Shop、Shopify 等销售环境。
平台内部还可能包含站点、区域、店铺和账户。

因此“SKU → SPU → 产品族 → Listing → 平台”不应被理解成一条严格的上下级链。

更准确的理解是：

- 产品族、SPU、SKU 描述产品结构；
- 平台、站点、店铺、Listing 描述销售结构；
- 两者通过带时间范围的映射关系连接。

## 为什么不要只依赖产品名称

假设名称采用：

~~~text
品牌 + 分类 + 型号 + 颜色 + 市场
~~~

看起来名称已经包含全部信息，但它会遇到几个问题：

- 品牌名称调整会导致整个名称变化；
- 分类标准变化后历史名称无法统一；
- 某些产品没有型号；
- 文本中的连字符和空格不一致；
- 同一个缩写在不同团队含义不同；
- 名称过长，不适合作为系统关联键；
- 通过拆字符串提取属性容易出错。

正确做法是：

- 使用稳定的内部标识关联数据；
- 将品牌、型号、分类、颜色和市场保存为独立字段；
- 产品名称用于展示；
- 名称变化保留历史记录。

名称像一句自我介绍，字段像身份证上的独立栏目。
自我介绍可以灵活变化，身份证字段则必须明确。

## 产品主表应该记录什么

### 标识与关系

- 内部产品 ID；
- SKU 编码；
- SPU ID；
- 产品族 ID；
- 父级或替代产品；
- 来源系统标识。

### 基础属性

- 标准名称；
- 品牌；
- 型号；
- 一级、二级和三级分类；
- 颜色；
- 规格；
- 材质；
- 市场；
- 包装版本；
- 单位。

### 业务属性

- 产品类型；
- 标准品、铺货品、配件或组合品；
- 是否可采购；
- 是否可销售；
- 生命周期状态；
- 负责人；
- 创建和停用时间。

### 治理属性

- 数据来源；
- 维护部门；
- 审核状态；
- 生效时间；
- 失效时间；
- 最后修改人；
- 修改原因。

不是所有字段都必须放在一张物理表中。
概念上需要区分对象、属性和关系，实施时再根据系统规模拆表。

## SKU 编码怎样设计

### 智能编码与无意义编码

智能编码把品牌、型号、颜色等信息塞进编码：

~~~text
NC-C01J-BLK-US
~~~

优点是人一眼可以理解。
缺点是属性变化后编码可能失真，而且编码会越来越长。

无意义编码只保证唯一：

~~~text
SKU00012345
~~~

优点是稳定，不受业务属性变化影响。
缺点是人无法从编码本身识别产品。

许多企业会采用折中方式：

- 内部主键使用稳定、无业务含义的 ID；
- 对外展示使用较短、可读的 SKU；
- 变化频繁的信息不进入编码；
- 编码一旦发生业务，不重复分配给其他产品。

### 编码原则

- 唯一：同一治理范围内不重复。
- 稳定：产品改名或换负责人不应导致编码改变。
- 可扩展：为未来产品保留空间。
- 少歧义：避免字母 O 与数字 0 等容易混淆的字符。
- 不复用：停用 SKU 的编码不分配给新产品。
- 有边界：明确编码在哪个组织和系统范围内唯一。

## 属性缺失怎样处理

铺货产品可能没有品牌或型号。
这不意味着必须编造一个值来填满字段。

至少应区分：

| 状态 | 含义 |
| --- | --- |
| 不适用 | 该类产品客观上不需要此属性 |
| 未知 | 理论上存在，但目前不知道 |
| 待确认 | 已有人负责核实 |
| 来源缺失 | 上游系统没有提供 |
| 历史缺失 | 旧数据无法追溯 |

空值不是一种统一含义。
如果数据库只保存空白，使用者无法区分“没有品牌”和“品牌还没录入”。

## 组合产品怎样管理

组合产品不能只写成：

~~~text
理疗仪 + 收纳盒 + 适配器
~~~

应该用结构化的物料清单记录：

| 组合 SKU | 组件 SKU | 数量 | 生效时间 | 失效时间 |
| --- | --- | ---: | --- | --- |
| SET-C01J-US | C01J-BLK-US | 1 | 2026-01-01 |  |
| SET-C01J-US | CASE-C01J | 1 | 2026-01-01 |  |
| SET-C01J-US | ADAPTER-US | 1 | 2026-01-01 |  |

这张关系表可以回答：

- 卖出一个套装消耗多少组件；
- 当前组件库存能组成多少套；
- 组合成本如何计算；
- 某一天使用的是哪个版本的组合。

### 虚拟组合与实物套装

虚拟组合可能在下单后才由仓库按组件拣货。
实物套装可能已经预先包装并拥有独立库存。

两者对库存扣减、成本和采购的处理不同，不能只用“都是组合产品”一概而论。

### 组合成本

最简单的组合成本是组件成本乘数量后求和。

但真实业务还可能包含：

- 组装人工；
- 新包装；
- 标签；
- 损耗；
- 不同批次成本；
- 平台配送费用。

因此产品关系负责说明“由什么组成”，成本规则负责说明“怎样计价”，两者不应混为同一字段。

## SKU 与 Listing 的映射

映射关系至少需要：

- 平台；
- 站点；
- 店铺；
- Listing ID；
- 平台 SKU；
- 内部 SKU；
- 映射类型；
- 生效时间；
- 失效时间；
- 数据来源。

为什么需要时间范围？

假设同一个 Listing 在 7 月 1 日更换了发货 SKU。
如果映射表只保存当前关系，1 月份的旧订单也可能被错误映射到新 SKU。

带有效期的关系像历史地图：你不仅知道道路现在通向哪里，也知道它过去何时改过方向。

## 产品分类体系

分类用于浏览、权限、报表和策略分析。

一个常见层次是：

~~~text
一级分类：健康护理
└── 二级分类：理疗设备
    └── 三级分类：TENS 理疗仪
~~~

分类设计需要避免两个极端：

- 太粗：所有产品都在“电子产品”下，无法分析。
- 太细：每个型号单独成为分类，分类失去聚合价值。

分类回答“属于哪一类”，型号回答“是哪一款”，两者不是同一概念。

企业内部分类也不必完全复制 Amazon 分类。
平台分类服务搜索和上架，内部分类服务经营管理，二者可以通过映射关联。

## 产品生命周期

产品状态可以设计为：

~~~text
草稿 → 待审核 → 有效 → 停售 → 停采 → 归档
~~~

状态需要说明允许的业务动作：

| 状态 | 可采购 | 可销售 | 可新建 Listing | 保留历史 |
| --- | --- | --- | --- | --- |
| 草稿 | 否 | 否 | 否 | 是 |
| 有效 | 是 | 是 | 是 | 是 |
| 停售 | 视规则 | 否 | 否 | 是 |
| 停采 | 否 | 可清库存 | 否 | 是 |
| 归档 | 否 | 否 | 否 | 是 |

已经进入订单、库存或财务数据的 SKU 不应物理删除。
停用状态能保留历史关联，同时阻止新业务继续使用。

## 新增与变更流程

### 新增产品

1. 业务提交新增申请。
2. 检查是否已有相同产品。
3. 确定产品族、SPU 和 SKU。
4. 填写必要属性。
5. 校验编码和分类。
6. 业务负责人审核。
7. 发布到 ERP、仓库和分析系统。
8. 记录生效时间。

### 修改产品

修改前先判断：

- 只是名称修正；
- 属性发生变化但仍是同一 SKU；
- 库存和交付发生实质变化，需要新 SKU；
- 核心产品定义变化，需要新 SPU。

例如产品负责人变化不应新建 SKU，但插头从 US 改为 UK 往往需要独立库存单位。

## 数据质量检查

产品主数据可以定期检查：

- SKU 是否唯一；
- 必填属性是否缺失；
- 品牌和分类是否使用受控值；
- SPU 是否存在；
- 组合组件是否形成循环引用；
- 组件数量是否大于零；
- Listing 是否存在有效 SKU 映射；
- 已停用 SKU 是否仍被新订单使用；
- 映射时间是否重叠；
- 同一产品是否被重复创建。

## 一个完整案例

假设企业销售 C01J 理疗仪：

~~~text
产品族：TENS 理疗系列
SPU：C01J 理疗仪
SKU：
  - C01J 黑色美国版
  - C01J 白色美国版
  - C01J 黑色英国版
组合 SKU：
  - C01J 黑色美国版 + 收纳盒
Listing：
  - Amazon US 页面 A
  - Amazon US 页面 B
  - Shopify US 页面
~~~

订单进入后：

1. 通过平台 SKU 找到 Listing 映射。
2. 将平台 SKU 转为内部 SKU。
3. 通过 SKU 找到 SPU 和产品族。
4. 如果是组合 SKU，展开组件关系。
5. 销售可以按 Listing、SKU、SPU 或产品族分析。
6. 库存按实际库存单位扣减。
7. 成本按组件和当时有效的成本规则计算。

这就是主数据把多个系统连接起来的过程。

## 常见误区

- 名称写得很完整，不等于主数据已经结构化。
- SKU、SPU、Listing 和 ASIN 不是同义词。
- 产品分类不是型号列表。
- 平台的父子变体不一定等于企业内部的 SPU 关系。
- 没有品牌的产品不应虚构品牌。
- 组合产品不是把两个名称拼起来。
- 停用不等于删除。
- 编码越长，不代表信息质量越高。
- 当前映射正确，不代表历史映射正确。

## 现阶段认知

产品主数据治理的核心不是设计一个漂亮编码，而是建立稳定身份、独立属性、明确关系和可追溯变化。

最终需要让企业能够回答：

1. 这件货在企业内部到底是谁？
2. 它属于哪个标准产品和产品族？
3. 它在哪些平台和 Listing 中销售？
4. 它是否由其他组件组成？
5. 关系从什么时候开始、什么时候结束？
6. 谁创建、审核和修改了它？
7. 历史订单为何仍能得到正确归属？

当这些问题能被稳定回答时，采购、库存、销售、成本和 BI 才拥有共同的产品语言。
