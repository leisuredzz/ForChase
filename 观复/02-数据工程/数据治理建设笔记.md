# 数据治理建设笔记

> **建议先读**：[[数据工程全景]]。
> **核验状态**：未核验——治理框架为整理时撰写，尚无来源标注与可复现的记录。详见 [[知识库质量审计]]。

这篇笔记解释数据治理为什么出现、治理哪些内容、如何在一家电商企业中逐步落地，以及它与数据仓库、主数据和数据质量之间的关系。

## 背景：有数据不等于能用数据

一家电商公司可能已经拥有很多系统：

- ERP 中有产品、采购和库存；
- Amazon、TikTok 和 Shopify 中有订单；
- 广告平台中有曝光、点击和花费；
- 财务系统中有收入、成本和费用；
- Excel 中有运营人员维护的补充信息；
- Power BI 中有各种报表。

从数量看，公司“到处都是数据”。
但老板询问本月销售额时，运营、财务和 BI 可能给出三个数字。

问题通常不在于缺少数据，而在于：

- 每个人采用不同的订单状态；
- 有人按下单日统计，有人按付款日统计；
- 有人包含税费，有人排除税费；
- 退款和取消订单的处理不同；
- SKU 在多个平台上的名称无法对应；
- 字段修改后没有留下记录；
- 数据出错时不知道由谁修复。

数据治理就是为多人共同使用的数据建立规则、责任和纠错机制。

可以把企业数据比作一座城市的交通系统：

- 数据标准像交通规则；
- 主数据像道路和地址编码；
- 数据质量像车辆年检；
- 权限管理像驾照和通行证；
- 元数据像地图和路标；
- 数据血缘像一件货物的物流轨迹；
- 责任机制像交警、道路养护和事故处理部门。

只有修路而没有规则，交通依然会混乱。
同样，只购买数据库或 BI 软件，并不会自动带来可信数据。

### 组织与责任

任何规则都需要有人负责。

常见角色包括：

- 数据所有者：对某一业务域的数据结果负责，通常来自业务管理部门。
- 数据管理员：维护定义、标准、质量问题和变更记录。
- 数据生产者：通过业务操作或系统流程创建数据。
- 数据开发者：负责采集、清洗、建模和交付。
- 数据使用者：通过报表、分析和模型使用数据。

责任不等于所有工作由一个人完成。
它的核心是出现问题时，能够明确谁解释业务、谁修改系统、谁验证结果。

### 数据标准

数据标准规定“大家如何说同一种语言”。

它可以包括：

- 字段命名；
- 数据类型；
- 日期和时区；
- 币种和汇率；
- 单位；
- 枚举值；
- 编码规则；
- 空值含义；
- 业务术语。

例如国家字段中同时出现 US、USA、United States 和 美国，会导致统计分裂。
标准不是为了追求形式整齐，而是为了让数据能够正确合并。

### 主数据

主数据描述企业反复使用的核心对象，例如产品、客户、供应商、店铺和组织。

它像企业的“统一通讯录”。
如果采购系统把某产品叫 A001，Amazon 使用 Seller SKU，ERP 又使用料号，就需要稳定的映射关系证明它们是否指向同一个产品。

产品主数据的详细内容见 [[产品主数据治理笔记]]。

### 指标口径

指标是管理决策中反复使用的度量，例如销售额、毛利率、库存周转率和广告投入产出比。

一个完整的指标定义至少包含：

| 内容 | 需要说明什么 |
| --- | --- |
| 业务含义 | 指标回答哪个业务问题 |
| 计算公式 | 分子、分母和计算步骤 |
| 统计粒度 | 按订单、SKU、店铺还是月份 |
| 时间口径 | 下单、付款、发货还是签收时间 |
| 数据范围 | 哪些平台、状态和业务类型 |
| 特殊处理 | 退款、取消、税费、折扣和汇率 |
| 更新频率 | 实时、每日还是月结 |
| 负责人 | 谁解释和批准口径 |
| 版本 | 何时生效，过去是否重算 |

例如：

~~~text
净销售额
= 商品成交金额
- 折扣
- 已确认退款
- 已取消订单金额
~~~

这仍然不完整。
还需要说明成交金额是否含税、退款按申请日还是完成日、跨币种如何换算。

### 数据质量

数据质量不是抽象的“数据要准确”，而是一组可以检查的规则。

| 维度 | 含义 | 电商例子 |
| --- | --- | --- |
| 完整性 | 必要字段不能缺失 | SKU、订单时间、数量不能为空 |
| 唯一性 | 业务主键不应重复 | 同一订单明细不能重复导入 |
| 合法性 | 值符合格式和范围 | 数量不能是无法解释的负数 |
| 一致性 | 不同位置表达一致 | 同一 SKU 的品牌应一致 |
| 准确性 | 数据反映真实业务 | 库存与实际盘点相符 |
| 及时性 | 在需要的时间内更新 | 每日库存应在报表刷新前到达 |
| 关联完整性 | 引用对象能够找到 | 订单 SKU 能映射到产品主表 |

质量规则应包含阈值和处理方式。
例如“订单 SKU 映射率必须达到 99.9%，未映射数据进入异常表并由产品管理员处理”，比“尽量保证映射完整”更可执行。

### 元数据

元数据是描述数据的数据。

它回答：

- 这张表叫什么；
- 每个字段是什么意思；
- 数据来自哪里；
- 多久更新一次；
- 谁负责；
- 保存多久；
- 有哪些下游使用者。

元数据像图书馆的目录卡。
没有目录，书仍然存在，但使用者很难发现和理解它。

### 数据血缘

血缘描述数据从源头到结果的加工路径。

~~~text
Amazon 订单 API
    ↓
ODS 原始订单
    ↓
DWD 订单明细
    ↓
DWS 店铺日销售
    ↓
Power BI 销售看板
~~~

当销售额异常时，血缘帮助定位是 API 少数、清洗逻辑错误、产品映射缺失，还是报表公式变化。

### 权限与安全

权限治理回答谁可以查看、修改和导出哪些数据。

常见原则：

- 最小权限：只授予完成工作所需的权限。
- 职责分离：创建、审批和审计不全部集中在同一人。
- 敏感数据保护：个人信息、密钥和财务数据需要更严格控制。
- 操作留痕：重要数据的访问和修改可以追溯。

### 数据生命周期

数据从产生到删除会经历创建、使用、归档和销毁。

并不是数据保存越久越好。
长期保存会增加成本、泄露风险和历史口径混乱。

生命周期规则需要说明：

- 哪些数据必须长期保存；
- 哪些只保留汇总；
- 何时转入低成本存储；
- 删除由谁批准；
- 删除后如何证明已经执行。

## 数据治理与数据仓库的关系

数据仓库是承载和加工分析数据的技术体系。
数据治理则定义数据的规则、责任和质量要求。

可以把数据仓库比作大型图书馆建筑，数据治理是分类法、借阅制度、编目规则和管理员体系。

只有仓库没有治理，可能出现：

- 表越来越多但没人知道哪张可信；
- 同一指标存在多个版本；
- 字段含义只能问原开发人员；
- 下游报错后无法追溯；
- 敏感数据被无控制地复制。

只有治理文件没有技术落地，则规则停留在纸面。
理想状态是规则进入表结构、质量检查、权限系统和开发流程。

## 如何从零开始建设

### 第一步：选择一个业务痛点

不要一开始试图治理所有数据。

适合试点的主题通常具备：

- 业务价值高；
- 问题反复发生；
- 范围可以控制；
- 能找到业务负责人；
- 结果可以验证。

产品或库存通常适合作为电商公司的起点。

### 第二步：盘点现状

以库存为例，需要列出：

- 哪些系统记录库存；
- 各系统中的仓库和 SKU 如何命名；
- 数据如何取得；
- 更新频率；
- 一行代表什么；
- 谁维护；
- 当前有哪些报表使用。

盘点不是为了制作漂亮文档，而是发现冲突和未知区域。

### 第三步：定义最小规则

例如库存主题的最小规则可以是：

- 统一内部 SKU；
- 统一仓库编码；
- 明确可售、在途、锁定和不可售库存；
- 明确快照时点与时区；
- 明确负库存如何解释；
- 明确每日更新时间；
- 明确未映射 SKU 的处理责任。

### 第四步：把规则做成检查

规则只有能够执行，才算真正落地。

可以每天检查：

- 是否缺少当天快照；
- SKU 是否重复；
- 数量字段是否为空；
- 是否存在未知仓库；
- 是否出现未映射 SKU；
- 总库存与源系统差异是否超过阈值。

### 第五步：建立问题闭环

一个质量问题需要经历：

~~~text
发现 → 分派 → 定位 → 修复 → 验证 → 关闭 → 预防
~~~

只生成异常报表而无人处理，不算完成治理。

### 第六步：逐步扩展

试点稳定后，再复用方法扩展到：

- 销售；
- 广告；
- 采购；
- 财务；
- 客户；
- 物流。

扩展的是方法和责任体系，不是机械复制同样的表。

## 一个指标冲突案例

假设三个报表的销售额分别为 1000 万、980 万和 1020 万。

排查可以分四层：

1. 数据范围：平台、店铺和时间是否一致。
2. 业务口径：退款、税费、折扣和取消订单是否一致。
3. 数据加工：连接是否造成重复，汇率是否正确。
4. 展示计算：Power BI 的筛选和度量是否一致。

治理的成果不是宣布某个数字“官方正确”，而是让所有人看到定义、过程和责任，并能重复计算出相同结果。

## 常见失败方式

### 把治理等同于买工具

工具可以管理目录、血缘和质量规则，但不能替企业决定“净销售额是什么”。

### 一开始建设过大体系

范围过大时，文档很多，业务感受不到改善，项目容易失去支持。

### 只有数据团队参与

数据团队能实现规则，却不能独自定义所有业务事实。
产品、财务、运营和供应链需要共同确认自己的领域。

### 追求字段完整而编造数据

未知就是未知。
用默认值掩盖缺失，会让质量问题变得更难发现。

### 规则没有版本

业务口径会变化。
如果不记录生效时间和是否回溯，历史报表会出现无法解释的跳变。

### 质量问题没有责任人

“系统有问题”不是可执行的结论。
必须区分源数据错误、采集失败、加工错误和业务定义冲突。

## 现阶段认知

数据治理不是一次性项目，而是一套持续运行的组织能力。

它的最小闭环是：

1. 给关键数据明确含义；
2. 指定维护责任；
3. 把规则变成可执行检查；
4. 发现异常后有人处理；
5. 修复后能够验证；
6. 变化时留下版本记录。

当企业能够稳定回答“这个数字是什么意思、从哪里来、谁负责、出了问题如何修复”，数据治理才真正产生价值。
