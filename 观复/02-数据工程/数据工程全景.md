# 数据工程全景

> **核验状态**：未核验——概念全景与类比为整理时撰写，尚无来源标注与可复现的运行记录。详见 [[知识库质量审计]]。

这篇笔记从一条数据如何走向报表出发，解释数据库、数据仓库、数据湖、ETL、Spark、Flink、Airflow 等概念各自解决什么问题。

## 背景：数据工程像一座城市的供水系统

业务数据就像分散在不同水源中的水：

- ERP 保存采购和库存；
- Amazon 保存订单和广告；
- Shopify 保存独立站交易；
- 财务系统保存收入和费用；
- Excel 保存临时表格；
- 日志记录用户点击和系统运行。

如果每个分析人员都自己拿桶去各处取水、过滤和计算，公司很快会出现同一个指标多个版本的问题。

数据工程的作用，类似建设城市供水系统：

- 采集是取水；
- 存储是水库；
- 清洗是净水厂；
- 调度是泵站控制；
- 建模是管网设计；
- 数据治理是水质标准；
- BI 和模型是居民、工厂等最终用户。

## 问题：工具很多，但它们不在同一层

Excel、SQL、MySQL、HDFS、Spark、Flink、Airflow 和 Power BI 经常出现在同一张学习路线里。
但它们分别是工具、语言、存储系统、计算引擎、调度平台或消费应用。

把它们理解为一条“新工具淘汰旧工具”的路线，会造成错误认识。
真实系统更像一支球队：不同位置同时存在，各自承担不同职责。

## 数据从哪里来

### 业务数据库

MySQL、PostgreSQL、SQL Server 和 Oracle 等数据库通常支撑业务系统。

它们强调：

- 及时写入；
- 事务一致性；
- 按主键查询；
- 同时处理大量小操作；
- 防止一笔业务只完成一半。

例如创建订单时，订单、明细和付款状态需要一致更新。
这种面向日常交易的系统通常称为 OLTP。

### API

API 像服务窗口。
外部系统不把整个数据库交给你，而是允许你按照约定提交请求并获得结果。

采集 API 数据需要处理：

- 身份认证和签名；
- 请求参数；
- 分页；
- 频率限制；
- 超时和重试；
- 增量边界；
- 返回字段变化；
- 重复数据；
- 错误日志。

### 文件与日志

CSV、Excel、JSON、Parquet 和应用日志也是常见数据源。

文件接入看似简单，但仍要回答：

- 文件是否完整上传；
- 编码和分隔符是什么；
- 同名文件会覆盖还是追加；
- 字段是否发生变化；
- 同一批数据是否重复处理。

## 数据如何进入分析系统

### ETL

ETL 是 Extract、Transform、Load：

~~~text
抽取 → 转换 → 加载
~~~

数据在进入目标系统之前完成清洗和转换。
这种方式适合目标结构明确、进入仓库前需要严格控制的场景。

### ELT

ELT 是 Extract、Load、Transform：

~~~text
抽取 → 加载原始数据 → 在目标平台转换
~~~

它先保存原始数据，再利用数据仓库或湖仓平台的计算能力处理。
优点是保留原始证据，规则改变时可以重新加工。

ETL 与 ELT 不是绝对对立。
例如采集时先做必要的格式校验，加载后再做复杂业务转换，就是两种思想的组合。

## 数据存在哪里

### 关系数据库

关系数据库像管理严格的档案室。
数据按照表、行、列组织，可以设置主键、外键、唯一约束和事务。

它适合结构清晰的数据和 SQL 查询。
小型团队也可以直接使用 PostgreSQL 或 MySQL 建立分析库，不必因为学习了“大数据”就立即引入分布式系统。

### HDFS

HDFS 是 Hadoop Distributed File System。
它把大文件分成块，分散存放在多台机器上，并通过副本应对部分机器故障。

类比一部超长电影：一台机器放不下，就切成多段存到多个仓库，同时为重要片段保留副本。

HDFS 主要解决大规模分布式文件存储，不负责定义企业指标，也不是业务数据库。

### 对象存储

对象存储以对象和键组织文件，常用于云上的数据湖。
与传统文件系统相比，它通常没有同样的目录和随机修改语义，但扩展性和耐久性较好。

### 行式存储与列式存储

行式存储把同一行的字段放在一起，像把一位客户的完整档案装进一个档案袋。
读取或修改单个对象时很方便。

列式存储把同一列的值放在一起，像把所有人的年龄放在一本册子里、所有人的收入放在另一本册子里。
分析只读取少数列时，可以减少扫描，并有利于压缩。

Parquet 和 ORC 是常见列式文件格式。
行式与列式各有适用场景，不是简单的先进与落后。

## 数据如何计算

### MapReduce

MapReduce 把大任务拆成两个基本阶段：

- Map：多个节点分别处理数据片段；
- Reduce：把局部结果合并成最终结果。

例如统计全国仓库库存：

1. 每个节点统计自己负责的仓库；
2. 再把各节点结果按 SKU 汇总。

MapReduce 的价值在于提供可靠的分布式计算模型，但多阶段任务频繁写入磁盘，开发和执行都较笨重。

### Spark

Spark 是通用分布式计算引擎，支持批处理、SQL、机器学习和流处理等工作负载。

它把计算描述成有依赖关系的任务图，并尽量复用中间结果。
可以把它想象成工厂调度员：先理解整条生产线，再安排哪些工序并行、哪些结果需要保留。

Spark 不是数据库，也不自动解决数据质量和指标口径问题。
是否需要 Spark，应由数据规模、计算复杂度、团队能力和现有平台决定。

### Flink

Flink 以有状态流处理见长。
它擅长处理持续到来的事件，并维护窗口、计数和业务状态。

例如实时计算过去五分钟的订单金额：

- 订单不断进入；
- 系统按事件时间分配窗口；
- 迟到数据需要规则处理；
- 发生故障后仍要恢复计算状态。

流处理的难点不只是“速度快”，还包括事件时间、乱序、状态、一致性和故障恢复。

## 数据如何按顺序运行

### 调度与编排

一个数据任务通常依赖另一个任务：

~~~text
订单采集完成
   ↓
订单清洗
   ↓
产品映射
   ↓
销售汇总
   ↓
刷新报表
~~~

Airflow 等工作流调度工具用于描述这些依赖、安排运行时间、记录状态和处理失败。

Airflow 像航空塔台：它安排飞机何时起降，却不是飞机发动机。
真正的数据转换可以由 SQL、Python、Spark 或其他系统执行。

systemd timer、cron 也能调度简单任务。
当任务数量少、依赖简单时，它们可能已经足够。

### 可靠运行需要什么

一个“每天成功”的任务至少要考虑：

- 幂等性：重复运行是否产生重复数据；
- 断点：失败后从哪里继续；
- 重试：哪些错误可以重试；
- 超时：卡住多久算失败；
- 日志：是否能定位失败位置；
- 告警：失败后谁会知道；
- 数据质量：程序成功是否等于数据正确；
- 依赖：上游未完成时是否阻止下游运行。

退出码为 0 只能说明程序自认为成功，不能单独证明业务结果正确。

## 数据库、数据仓库、数据湖与湖仓一体

### 数据库

数据库主要服务日常业务操作。
它像收银台系统，必须快速、准确地处理一笔笔交易。

### 数据仓库

数据仓库服务跨系统分析。
它像企业的中央分析中心，把订单、产品、库存、广告和财务数据按照统一定义组织起来。

数据仓库强调：

- 面向主题；
- 历史积累；
- 跨系统整合；
- 稳定口径；
- 面向分析的模型。

### 数据湖

数据湖保存大量原始或较少加工的数据，包括表格、日志、图片和文件。
它像一个容量巨大的原料仓库，允许先保存，再决定未来怎样使用。

缺少目录、质量、权限和生命周期管理时，数据湖可能退化成“数据沼泽”：东西很多，却找不到、看不懂、也不敢用。

### 湖仓一体

湖仓一体试图在低成本、开放的数据湖存储上，增加数据仓库常见的能力：

- 表结构和模式管理；
- 事务一致性；
- 版本与时间旅行；
- 更新和删除；
- 查询优化；
- 多计算引擎协作。

它不是一个单独产品，也不是简单地把“湖”和“仓”两个词放在一起。

## 一条完整的电商数据链路

~~~mermaid
flowchart LR
    A[Amazon / ERP / Shopify] --> B[API与文件采集]
    B --> C[原始层 ODS]
    C --> D[清洗后的明细层]
    D --> E[产品与店铺维度]
    D --> F[销售与库存主题汇总]
    E --> F
    F --> G[Power BI / API / 数据科学模型]
~~~

以库存为例：

1. Python 请求领星 API，并处理分页。
2. 原始响应及同步时间进入 ODS。
3. 清洗数量、仓库、SKU 和日期字段。
4. 用产品主数据把平台 SKU 映射到内部产品。
5. 形成仓库 × SKU × 日期粒度的库存快照。
6. 计算缺货率、库存周转和库龄等指标。
7. Power BI 使用稳定的数据集，不再重复实现底层清洗。

## 数据工程与数据科学的关系

数据科学关注从数据中推断规律、评估不确定性和建立模型。

数据工程保证模型获得稳定、可解释和可重复的数据输入。

可以把数据科学家比作厨师，数据工程师比作供应链和厨房基础设施。
再好的厨师，如果食材缺失、标签错误、每天送达格式不同，也很难持续做出可靠结果。

两者的交界包括：

- 特征数据的定义；
- 训练数据版本；
- 离线训练与在线推理的一致性；
- 数据漂移；
- 模型输入质量；
- 实验可复现性。

## 常见误区

- 数据量不大，也可以建设清晰的数据工程流程。
- 使用 Spark 不等于拥有数据仓库。
- 使用 Airflow 不等于完成 ETL。
- 把文件放进对象存储不等于建成数据湖。
- 建了分层表，不等于指标口径已经统一。
- 程序运行成功，不等于数据质量合格。
- 实时不天然优于批处理；业务不需要时，实时只会增加复杂度。
- 工具越多不代表架构越成熟。

## 现阶段认知

理解数据工程时，先把问题分成六类：

1. 数据从哪里来？
2. 数据怎样被可靠采集？
3. 数据存在哪里？
4. 数据由什么引擎加工？
5. 任务如何调度和监控？
6. 数据最终如何被业务、报表或模型消费？

只有把这六类问题连接起来，数据库、Spark、Flink、Airflow、数据湖和数据仓库才会从一堆名词变成一张完整地图。
