# 观复知识库规则与更新流程

## 一、知识归属：先找概念的家

| 位置 | 负责的问题 | 边界 |
| --- | --- | --- |
| `00-数据基础` | 数据类型、业务语义、粒度、统计描述 | 是 Python、SQL、数仓和报表共享的地基；不放某个软件的操作 |
| `01-编程与开发` | Python 语言与生态库、Git、调试、部署 | pandas 属于 Python；跨系统采集案例归数据工程 |
| `02-数据工程` | SQL、采集、数据仓库、治理、主数据 | 从数据来源到可信交付；不放报表页面设计 |
| `03-数据分析与报表` | 业务问题、指标、Power BI 建模与表达 | Power Query、DAX 和可视化均属 Power BI 工作流 |
| `04-智能系统` | AI 应用结构与机制 | 具体 Python 实现仍链接编程体系 |
| `05-业务领域` | 金融等业务领域的概念与约束 | 方法与工具回链，不复制 |
| `90-个人` | 个人写作 | 保留作者原意 |

文件夹表达**知识归属**，阅读顺序由依赖关系表达。一篇主笔记只放一个位置；跨领域用链接。原始材料先进入 `待入库`，完成处理后成为主笔记中的知识、必要附件或被清理的冗余材料；不设永久的中间态分类。

## 二、知识生长：先修关系必须真实

1. 从共享概念出发，再到方法、系统、应用与案例。[[首页]] 是统一的阅读入口，区分并行分支；不把编号或文件夹顺序当成所有人的必修课。
2. 只有“缺少 A 就无法理解 B 的核心内容”才写 A 是 B 的**先修**；仅能提高阅读效率的写“建议阅读”。不要给起点笔记批量添加“前置：无”。
3. 新材料先寻找落脚点：同一问题且可合并则**修订既有笔记**；一篇同时回答两个独立问题且过长则**拆分**；知识缺口真实存在才**新建**。避免同时维护两份同义解释。
4. 根概念在其所属笔记讲清楚；下游笔记给一个够用的提示并链接回源头。案例记录场景、约束、决策、结果和失败，不重写语言或数据库教程。

## 三、载体：让知识采用最适合的形式

**转换格式不是重构知识。** 一份材料转为 Markdown，只有在核对事实与来源、提炼概念、修正错误，并与已有知识合并或拆分后，才算完成入库。新笔记必须在准确性、可理解性和使用效率上至少不弱于原材料；否则继续加工，不以“已转写”为由删除仍有独特价值的原件。

**奥卡姆剃刀约束冗余实体，不以缩短篇幅为目标。** 合并重复解释时，保留各处独有的概念、原理、步骤、参数语义、前提、反例、排错方法和可执行示例。概括句或章节标题不能代替原本可学习、可操作的内容；不要把详细教程降级成提纲或速查表。

**判据有两维，只看形式不够。** ①**哪种形式更适合**——在“读、查、用”三件事上是否真的更好；②**内容是什么性质**——知识性内容重在可检索、可复用，能被更准确地重构，原件就由重构后的知识取代；人文与思想性内容（个人写作、信件等带作者语气与版式的表达）**原件本身就是实体**，Markdown 只作转写副本并指向原件，不因“已经转录”而清理。

**判据由用户给定，不由整理者自定。** 不得把它替换成更省事的版本（例如“截图一律转录后删图”），也不得用自己刚写下的规则为删除背书——那是既立法又执法。同级材料的形式判断必须一致，不能同一类载体在相邻两次处理里得到相反结论。

1. **Markdown 足以更好地表达**：浅显清单、代码截图、重复说明等，融入现有笔记或写成必要的新笔记。核对无独有信息后，由重构后的知识取代原件；不同时保存一份低质摘要和一份无必要的原件。
2. **原形式有不可替代的价值**：例如图片的空间布局、电子表格的公式与交互、文档的关键版式，或核验结论所必需的原始证据。只保留实际需要的文件，统一放入 `附件/`；按现有知识主题分组，不预建空目录。同一素材只存一份，由相关主笔记说明用途并嵌入或链接。能写进 Markdown 不等于原件无用，不能仅凭可转写就删除。
3. **尚未判断或核验**：留在 `待入库`，不凭文件大小或篇幅直接晋升为主笔记、附件或永久参考区。处理后只有三种去向：知识融入 Markdown、必要原件进入 `附件/`、无必要的中间稿和冗余原件被清理。
4. **导图按同一标准判断**：必须查看原图并检查节点、摘要、备注、图片和外链。有独特布局价值且被主笔记使用的图片或可编辑文件可留作附件；其余内容融入 Markdown 后清理导图与转写稿。对已删除资料，不声称仍可打开，也不凭记忆重建缺失内容。

每次处理完成后检查：主笔记是否比原材料更准确、更易用；附件是否有明确用途和至少一处有效引用；两份材料是否只是重复。引用外部来源时保留 URL、书名与章节等可核查线索，无须为一个指针另建索引页。

删除原件前逐项核对：原件中独有的事实、数据、代码、出处和个人表达，分别进入哪篇笔记的哪一节；未迁入的内容为何确属错误、重复或无保留价值；原件是否承担版式、交互或证据作用。若无法回答，就继续加工或保留为必要附件，不先删除。个人信件等需要保留原始表达或版式的文件，也按主题放入 `附件/`，由对应 Markdown 指向原件。

核对粒度须落到知识点与操作，不仅是“整章已覆盖”。有独立价值但未实测的内容，应保留并标明来源、待核验条件；“未实测”不能直接作为删除理由。错误命题应修正，同时保留它试图回答的问题和有效的操作能力。若用户指出重构丢失知识，以提供的原稿逐项补足并完成内部核对，再由重构后的知识取代原件。

Obsidian 新增附件先落入 `附件/`；处理时移至该目录下合适的主题分组，并修正引用。不要将 Word、图片等原件散落在主知识目录。

## 四、证据：事实、推断与核验边界

1. 区分用户经验、外部作者观点、AI 补充、实测结果和推断。关键定义、数字、公式、命令与 API 行为优先核对原始或官方资料。
2. 写清核验的范围、环境和方法。一次代码运行只证明该输入与环境；SQLite 运行结果不能替代 MySQL 实测；结构检查不等于事实核验。
3. 没有足够证据时标“待核验”或留在 `待入库`，不用流畅叙述掩盖不确定性。个人写作保持原意与语气。
4. 对容易争议或随版本变化的技术结论，记录可复现的最小输入、查询或操作、运行环境与版本、预期及实际结果，并附官方或原始来源。明确区分亲自运行、文档核对与推断；无法复现时写明限制，不将一次观察推广为通用规律。

**核验状态写在每篇主笔记顶部。** 位置在 H1 之下、导语上方的引用块内，一行 `> **核验状态**：…`，取值只用下面五个，并在同一句里说清核到什么程度、缺什么：

| 取值 | 含义 |
| --- | --- |
| `已实测` | 在本机运行或引擎求值过，须写明环境与看到的结论 |
| `部分实测` | 只有部分结论有运行记录，须写明是哪一部分 |
| `文档核对` | 对照官方文档或规范，未在本机复现 |
| `未核验` | 尚无来源标注或可复现的运行记录 |
| `不适用` | 个人写作等不做事实核验的内容 |

写“未核验”不等于内容有错，只是把“还不知道”放到读者看得见的地方；它的反面不是“已核验”，而是“没人知道核到什么程度”。取值随核验进展改变，改变的凭据记进 [[知识库质量审计]]。`维护/检查知识库.py` 会检查每篇知识笔记是否有这一行、取值是否在规定范围内。

## 五、每次“更新”的流程

1. 确认工作目录是包含本文件、`首页.md` 与 `待入库` 的 **观复**；先盘点新文件和现有相邻笔记，再编辑。
2. 按“融入既有笔记／拆分／新建／保留必要附件／清理”逐项决定，处理正文、附件与回链；按第三节的逐项核对要求完成删除前检查。`待入库` 只作处理入口：完成重构与内部质量检查后清理已被取代的原件，不另留对照副本，也不等待用户验收。用户核对入库后的笔记，提出问题时继续修订；有不可替代形式价值的材料按第三节进入附件库。
3. 更新 [[首页]] 中受影响的学习路径，检查跨主题链接，运行 `维护/检查知识库.py`，另核查新增附件、关键内容，以及改动笔记的核验状态行是否与新内容一致。
4. 在 [[知识库质量审计]] 记录本次验证的事实、复现条件及未验证范围；确认内容和结构后运行 `维护/备份观复.py`。脚本先检查知识库，再生成并校验新压缩包，成功后覆盖上一份快照；失败时保留旧快照。备份放在库外的 `文档/观复备份/观复.zip`，只保留这一份，不在库内复制历史版本。
5. 向用户报告具体变更、理由、验证结果和缺口。备份与原库位于同一磁盘时，它能应对误改和误删，不能应对整盘故障。

## 六、规则、审计与日志各司其职

- **本文件**只写长期有效的分类、依赖、载体与证据原则；不追加工作流水或日期记录。
- **[[知识库质量审计]]**记核验范围、结果、错误与待核验事项；不要把“通过结构检查”写成“内容正确”。
- **`.workbuddy/memory/`** 只记尚未进入规则、尚未解决的偏差与未决项。**教训一旦写进本文件就算已经消化：整理前不需要读日志**，只在要追溯某次判断为什么出错时才查；能在当次直接改规则的，就改规则，不再另写一条日志。日志不复制本规则，也不以历史条目覆盖现行规则。

同一个原则只在上述三处表达（本文件、[[知识库质量审计]]、日志），外加技能与 [[首页]] 中的引用。四处不会自动保持一致，改动规则时须逐一检查，其中任何一处过期都不会被结构检查发现。

用户当次明确指令优先。若新要求改变了分类或载体原则，先调整本文件和首页，再执行具体迁移，避免规则与磁盘现状分叉。
