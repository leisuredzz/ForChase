# 调试与排错方法

> **核验状态**：未核验——方法框架为整理时撰写，尚无来源标注与可复现的运行记录。详见 [[知识库质量审计]]。

## 背景：排错慢，慢在哪

一段程序出错，通常有三种反应：

1. 看不懂报错，直接搜报错信息的最后一行，抄别人的答案；
2. 猜一个可能的原因，改一处，重跑；
3. 从日志和调用栈出发，先确定错误发生在哪一层，再缩小范围。

第 3 种最快，但大多数人默认用第 2 种。原因很实际：**第 2 种在开始时不费脑力**。改一行、重跑、看结果，动作很短，反馈很快。它的问题是，每一轮都不产生新知识——猜错了，你对问题的理解还是零；于是容易进入"改十处、跑十次"的循环。

第 3 种前期更慢，但每一步都在**排除一个范围**。跑三次之后，第 2 种还剩一大堆未知，第 3 种已经把范围压到一两行代码。

## 问题：为什么"改一下试试"往往更慢

因为**多数错误的位置，比它表现出的位置更早**。

一个典型例子：日志说"写库时报 `Unknown column 'raw_data'`"，看起来是数据库的问题。但真正的原因可能是上游 JSON 结构变了，某个字段没取到，于是插入时列对不上。如果直接去改数据库表结构，问题会被掩盖——数据错着写进去了，只是不再报错。

这类错误的共同点是：**报错点 ≠ 根因点**。所以排错的第一步不是"改哪里"，而是"**确定错误发生在哪一层**"。

## 一、先定位层，再动手

把一条数据链路的执行过程切成几段，每段只可能出某几类问题：

| 现象 | 出问题的层 | 该看什么 |
| --- | --- | --- |
| 命令还没启动代码就失败 | 运行时／构建／入口层 | 解释器版本、依赖、入口配置 |
| 代码启动了但找不到配置 | 路径／环境变量层 | 工作目录、`.env`、环境变量 |
| 请求发不出去 | 网络层 | DNS、超时、TLS、HTTP 状态 |
| 收到了但业务失败 | 业务协议层 | 鉴权、权限、参数、接口版本 |
| 解析响应报错 | 数据层 | JSON 结构、字段类型、空值 |
| 数量对不上 | 逻辑层 | 分页边界、去重、结束条件 |
| 写库报错 | 存储层 | 表结构、列名、类型、权限、事务 |

**规则只有一条：只在对应的层处理问题。** 构建失败时去改数据库表，无论改多少遍都不会有帮助——但这样做会消耗掉一整个下午，并让你对系统产生错误的印象。

这一步的价值在于它是**纯观察**：不需要改代码，只需要问"程序走到哪一步了"。

## 二、读 traceback 的正确顺序

Python 的调用栈是倒着的——最后一行才是错误本体。所以从后往前读：

1. 先读**最后一行**：错误类型和核心信息；
2. 从下往上找**第一个属于自己项目的文件**（跳过第三方库）；
3. 看它的**绝对路径和行号**——确认你改的确实是正在运行的那份文件；
4. 看该行**收到的实际数据**是什么类型、什么值；
5. 最后才判断根因。

~~~text
第三方库内部很多行（先跳过）
        ↓
src/main.py 第 299 行  executemany
        ↓
Unknown column 'raw_data'   ← 先看这里
~~~

第 3 步容易被跳过，但它挡住了一类高频问题：**你改的文件不是正在运行的那份**。同一个项目在本地和服务器各有一份、虚拟环境装的是旧版本、IDE 缓存了旧字节码——都会让"明明改了却没生效"。看到绝对路径，这类问题两秒就能排除。

## 三、最小验证：每次只验证一个假设

把一次完整的运行拆成一串可单独验证的台阶，从最里面往外走：

~~~text
① 程序入口能启动
② 配置能正确读取
③ 鉴权／凭据能拿到
④ 单次请求成功
⑤ 返回结构符合预期
⑥ 少量数据（2~3 条）能转换
⑦ 小批量能写入测试表
⑧ 最后才跑全量
~~~

两个要点：

- **每次只验证一个假设**。同时改三处再重跑，即使成功，你也不知道是哪一处起了作用——下一次遇到同类问题，你还是不会。
- **不要一上来就跑全量**。全量失败时，你面对的是"一千条里有一条不对"，定位成本远高于"两条里有一条不对"。

这与 [[Python文件异常与测试]] 讲的"最小有效测试"是同一个思路，只是从写测试的阶段提前到了排错的阶段。

## 四、调试输出应该回答问题

临时打印的目的不是"看看有什么"，而是**回答一个具体疑问**。写之前先想清楚它要排除什么。

值得打印的：

~~~python
print("执行文件:", __file__)          # 我改的是这份吗
print("目标地址:", URL)                # 路径对不对
print("返回类型:", type(data).__name__) # 是 dict 还是 list
print("本页条数:", len(page))           # 分页进展
print("累计条数:", len(rows))           # 与预期总数比
~~~

不该打印的：

- 密钥、AppSecret；
- 完整的 access_token；
- 数据库密码；
- 未脱敏的整批业务数据。

**日志会长期留存**，临时调试输出很容易被忘在代码里，或者被写进日志文件。所以"不打印秘密"不是谨慎，是必须——尤其当这个仓库会被同事看到或推到远端时。

## 五、重试与容错的边界

"加个重试"是常见的第一反应，但它只对一部分错误有效。

| 适合重试 | 不适合盲目重试 |
| --- | --- |
| 短暂网络抖动 | 地址或路径写错 |
| 请求超时 | 参数缺失 |
| 服务端 5xx | 没有权限 |
| 明确的限流（按要求等待） | 签名／鉴权算法错误 |
| | 表结构或列名不对 |
| | 类型处理错误 |

判断依据：**这个错误再试一次，外部条件会不会变？** 网络抖动会变，所以值得重试；参数写错不会变，重试一万次还是同一个错误，只会拖长失败时间、放大日志。

重试还必须设**最大次数**并逐步拉长间隔，否则容易变成死循环——尤其在限流场景下，密集重试反而会让对方把你封得更久。

## 六、把上面五步合成一个流程

~~~mermaid

    B -->|先别改| C[定位：错误在哪一层]
    C --> D[读 traceback：找到自己文件的行]
    D --> E[最小验证：一次一个假设]
    E --> F{解决?}
    F -->|否| C

    style C fill:#FAEEDA,stroke:#854F0B,stroke-width:0.5px
~~~

流程里最容易漏掉的是最后一步。**问题解决后要留下证据**：一条能回答"这次跑了多少行、写入了多少行"的日志，比下次再排查一遍便宜得多。这也是 [[数据工程全景]] 里"可靠运行需要什么"那一段讲的可观察性。

## 常见误区

1. **看到报错就改报错的那一行**——报错点常常不是根因点。
2. **一次改多处**——成功了也不知道是哪一处起作用。
3. **跳过"改的是不是正在运行的那份文件"**——最高频、最容易排除、却最常被忽略。
4. **一上来跑全量**——把定位问题变成大海捞针。
5. **盲目加重试**——对参数错误、权限错误、类型错误完全无效。
6. **没有最大重试次数**——网络类故障下会把失败时间拖得很长。
7. **打印密钥和完整 token**——日志会长期留存。
8. **用 `print` 做长期日志**——临时输出容易残留，也无法分级和检索。
9. **问题解决后不留日志**——同一个问题下次还要重排一遍。
10. **只关注会报错的错误**——静默算错的数据往往代价更高。

## 现阶段认知

排错能力和"写了多少行代码"关系不大，和**提问方式**关系很大。

新手问的是"这里为什么报错"；熟练的人问的是"程序走到哪一步了"、"证据是什么"、"这层的输入按理说该是什么样"。前者指向答案的抄写，后者指向范围的缩小。

还有一个反直觉的点：**排错能力有一大半是在写代码时决定的**。边界清晰、失败时有明确日志、每步都能单独验证的程序，出错时容易定位；而一大坨连在一起、只在最后打印结果的程序，即使作者本人也难查。所以[[Python文件异常与测试]]里说的"明确边界"，不只是代码质量问题，它直接决定了未来排查的成本。
