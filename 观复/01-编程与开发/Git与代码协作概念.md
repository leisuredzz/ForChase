# Git与代码协作概念

> **核验状态**：未核验——概念整理，尚无来源标注与可复现的运行记录。详见 [[知识库质量审计]]。

这篇笔记从“为什么需要版本控制”开始，解释 Repository、Commit、Branch、Merge、Remote、GitHub 和 Pull Request 之间的关系。

## 背景：普通保存解决不了哪些问题

写代码或文档时，人们常用这种方式保存版本：

~~~text
项目-最终版
项目-最终版2
项目-最终版-真的最终版
项目-最终版-改回昨天
~~~

这种方法很快会遇到问题：

- 不知道两个版本改了什么；
- 不知道为什么修改；
- 多人修改后无法合并；
- 删除内容后难以找回；
- 新功能做到一半，影响稳定版本；
- 无法确定某次发布对应哪份代码。

Git 是分布式版本控制系统。
它不只是备份文件，而是记录“哪些内容在什么时间、因为什么目的发生了变化”。

可以把 Git 想象成一本带分支的时光档案：

- 文件是稿件；
- Commit 是一次有说明的快照；
- Branch 是一条独立修改路线；
- Merge 是把两条路线汇合；
- Remote 是存放在另一台机器上的仓库；
- GitHub 是围绕远程仓库提供协作服务的平台。

## Repository：版本历史的容器

Repository 通常翻译为仓库。
它包含项目文件、Git 配置和版本历史。

执行初始化后，项目中会出现隐藏的 Git 数据目录。
这个目录保存对象、引用和配置，不应当像普通源码那样随意修改。

仓库可以存在于：

- 本地电脑；
- 公司服务器；
- GitHub、GitLab 等托管平台；
- 多个位置同时存在。

Git 是分布式的，这意味着每个完整克隆通常都拥有自己的历史副本。
即使暂时离线，也可以在本地查看历史、创建提交和切换分支。

## 三个区域：理解 Git 的关键

初学者最容易困惑的，是“文件已经保存了，为什么还没有提交”。

Git 可以用三个区域理解：

~~~mermaid
flowchart LR
    W[Working Tree 工作区] -->|git add| S[Staging Area 暂存区]
    S -->|git commit| R[Repository 本地仓库]
    R -->|git push| REM[Remote 远程仓库]
~~~

### Working Tree

工作区是你当前看到和编辑的文件。

按下编辑器的保存键，只是把内容写入工作区。
Git 会发现文件与上次提交不同，但不会自动创建新版本。

### Staging Area

暂存区用于选择“哪些变更进入下一次 Commit”。

假设你同时：

- 修复了一个计算错误；
- 修改了 README；
- 写了一半新功能。

你可以只把计算错误加入暂存区，先创建一个清晰的修复提交。

暂存区像寄快递前的打包台。
家里有很多物品发生变化，但只有放进包裹的东西会被本次寄出。

### Repository

Commit 创建后，版本进入本地仓库。

这时历史已经在本机形成，但还没有自动上传到 GitHub。

## Commit：一次有意义的变化

Commit 不是简单的“保存按钮”，而是一个版本节点。

它通常记录：

- 本次项目状态；
- 父提交；
- 作者；
- 时间；
- 提交说明。

好的 Commit 应围绕一个可以解释的目的。

例如：

~~~text
修复退款订单重复计入净销售额
~~~

比下面的说明更有价值：

~~~text
改了一些东西
~~~

提交说明应帮助未来的人回答：

- 为什么改；
- 改变了什么行为；
- 出现问题时应查看哪里。

### 快照与差异

理解上，可以把 Commit 看作项目在某个时点的快照。
Git 会高效复用相同内容，并能够展示两个版本之间的差异。

版本历史的价值不只在于回退，也在于追查：

- 某一行是谁修改的；
- 错误从哪个版本开始；
- 某项设计为何出现；
- 发布版本包含哪些变化。

## Branch：并行工作的路线

Branch 通常翻译为分支。
它本质上是指向某个 Commit 的可移动引用。

可以把项目历史想象成铁路线：

~~~text
A──B──C  main
    +     D──E  feature
~~~

main 保存稳定主线，feature 用于开发新功能。
在 feature 上创建 Commit，不会自动改变 main。

分支适合：

- 开发功能；
- 修复缺陷；
- 尝试实验；
- 准备发布；
- 隔离不同任务。

分支不是完整复制一套项目文件。
Git 通过历史和引用高效管理这些路线。

### HEAD

HEAD 表示当前检出的版本位置。
通常它指向当前分支，当前分支再指向最新 Commit。

创建新 Commit 时，当前分支向前移动。

## Merge 与 Rebase

### Merge

Merge 把两条历史合并。

如果分支之间没有冲突，Git 可以自动组合变化。
必要时会创建一个合并提交，记录两条路线在此汇合。

### Rebase

Rebase 把一组提交重新放到新的基础之上，使历史看起来更线性。

它会重写相关提交的身份，因此对已经共享的历史要谨慎使用。

初学阶段可以先掌握：

- 用分支隔离任务；
- 用 Merge 合并；
- 不随意重写其他人已经使用的公共历史。

## 冲突为什么发生

当两条分支修改同一文件的同一区域，Git 无法确定应该保留哪一方，就会产生冲突。

冲突不是系统故障，而是需要人做业务判断：

~~~text
一方把销售额改为含税
另一方把销售额改为扣除退款
~~~

Git 能指出两个变化，却不知道最终口径应该是什么。

解决冲突通常需要：

1. 阅读双方改动；
2. 理解各自目的；
3. 编辑成最终结果；
4. 运行测试或检查文档；
5. 标记冲突已解决；
6. 完成合并。

## Remote：远程仓库

Remote 是本地仓库保存的远程位置名称和地址。

常见默认名称是 origin，但它只是约定，不是固定规则。

本地与远程是两个独立状态：

- Commit 只创建本地历史；
- Push 把本地提交发送到远程；
- Fetch 获取远程的新历史，但不自动合并；
- Pull 通常获取并整合远程变化。

因此：

> 保存文件 ≠ 暂存 ≠ Commit ≠ Push。

这是四个不同动作。

## GitHub 是什么

GitHub 不是 Git 的另一个名字。

Git 是版本控制系统，GitHub 是托管 Git 仓库和组织协作的平台。

GitHub 还提供：

- 权限管理；
- Pull Request；
- Issue；
- 代码审查；
- 自动化工作流；
- 发布管理；
- 项目看板；
- 安全检查。

不用 GitHub 也可以使用 Git。
同样的仓库也可以托管在 GitLab、Bitbucket 或公司内部服务器。

## Pull Request：把变更交给团队审查

Pull Request 通常简称 PR。
它不是 Git 核心命令，而是托管平台提供的协作对象。

PR 表达：

> 我在这个分支完成了一组变化，希望经过讨论和检查后合入目标分支。

一个清晰的 PR 应说明：

- 解决什么问题；
- 最终行为如何变化；
- 为什么采用这种方案；
- 怎样验证；
- 有哪些风险和限制。

代码审查可能关注：

- 逻辑是否正确；
- 是否遗漏边界情况；
- 是否符合项目规范；
- 测试是否充分；
- 命名是否清楚；
- 是否引入安全或性能问题。

PR 不只是审批，也是一份技术沟通记录。

## 标签与发布版本

Tag 给某个 Commit 添加稳定名称。

例如：

~~~text
v1.0.0
v1.1.0
~~~

分支会随着新提交移动，标签通常用于固定指向一个发布节点。

发布系统可以使用标签构建安装包、镜像或部署版本。

## .gitignore：哪些文件不进入版本控制

.gitignore 用来声明通常不应纳入版本控制的文件，例如：

- 虚拟环境；
- 缓存；
- 构建产物；
- 本地临时文件；
- 编辑器状态；
- 含密钥的环境文件。

.gitignore 不会自动移除已经被 Git 跟踪的文件。
已经提交过的敏感信息即使后来删除，也可能仍存在历史中。

因此密钥、Token 和密码不应进入提交。

## 一套基本协作流程

~~~text
更新本地主线
    ↓
为任务创建分支
    ↓
修改并查看差异
    ↓
选择变更进入暂存区
    ↓
创建清晰 Commit
    ↓
推送远程分支
    ↓
发起 Pull Request
    ↓
自动检查与人工审查
    ↓
合并到主线
~~~

常用命令的职责：

| 命令 | 作用 |
| --- | --- |
| git status | 查看工作区和暂存区状态 |
| git diff | 查看尚未暂存的差异 |
| git add | 选择进入暂存区的变化 |
| git commit | 创建本地提交 |
| git log | 查看历史 |
| git switch | 切换分支 |
| git branch | 查看或管理分支 |
| git fetch | 获取远程历史 |
| git pull | 获取并整合远程变化 |
| git push | 推送本地提交 |

## Git 与数据项目

Git 适合管理：

- Python 代码；
- SQL 脚本；
- 数据模型定义；
- 指标口径文档；
- 配置模板；
- 数据质量规则；
- 小型示例数据。

Git 通常不适合直接管理：

- 大型数据库文件；
- 每日完整数据导出；
- 含个人或商业敏感信息的数据；
- 频繁变化的大型二进制文件；
- 密钥和令牌。

数据本身的版本可能需要对象存储、数据湖表格式、数据目录或实验追踪工具。
“代码版本”和“数据版本”相关，但不是同一个问题。

## 常见误区

- 保存文件就是 Commit。
- Commit 后代码已经上传 GitHub。
- GitHub 就是 Git。
- 分支是复制了一份完整项目。
- Merge 冲突代表某一方写错了。
- Pull 会简单覆盖本地内容。
- 删除敏感文件后，历史中也自动消失。
- 每次提交越大越省事。
- Git 可以替代数据库备份。

## 现阶段认知

理解 Git 时，记住两条主线。

第一条是内容怎样进入历史：

~~~text
工作区 → 暂存区 → 本地 Commit → 远程仓库
~~~

第二条是团队怎样并行协作：

~~~text
主分支 → 任务分支 → Pull Request → 审查 → 合并
~~~

Git 的真正价值不是让人永远不犯错，而是让变化可见、可解释、可比较，并在多人协作中保留清晰历史。
