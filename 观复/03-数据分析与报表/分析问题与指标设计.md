# 分析问题与指标设计

> **先修**：[[数据认知框架]]。本篇把数据的业务含义落实为可回答的问题和可复核的指标；具体建模工具见 [[Power BI 分析与建模]]。
> **核验状态**：未核验——方法整理，尚无来源标注与可复现的记录。详见 [[知识库质量审计]]。

## 背景：先有决策，后有数字

一张报表首先要回答“谁需要据此做什么决定”。如果问题只是“展示销售数据”，页面可以无限加图，却没有办法判断哪些数字必须准确、哪些维度值得拆开。

以“本周退货率是否异常”为例，需要先问：异常相对哪个基线？用于发现问题还是评估措施？谁会在看到结果后行动？这些问题确定后，才值得定义退货率、时间窗口与下钻维度。

## 从问题到指标

| 层次 | 本例要写清楚的内容 | 典型错误 |
| --- | --- | --- |
| 决策 | 是否排查某产品或渠道的退货原因 | 只要求“做个退货看板” |
| 对象 | 哪些订单进入统计，是否包含取消、换货和测试单 | 不同页面使用不同订单集合 |
| 事件 | 退货以申请、审核还是完成为准 | 分子与分母处于不同业务阶段 |
| 时间 | 按下单日、退货申请日还是完成日归属 | 把本周退货除以本周下单，误当同一批订单 |
| 粒度 | 一行是订单、订单明细还是退货明细 | 一次订单多件商品被重复计数 |
| 维度 | 产品、渠道、地区、用户群等 | 维度键不唯一，连接后行数膨胀 |
| 验收 | 选取一组可手算样本，核对分子、分母和边界单 | 只检查图表外观 |

同名指标可能有多种合法口径。先写文字定义，再给计算式。例如“按下单周统计、在观察期内已完成退货的订单明细数 ÷ 同批订单明细数”与“本周完成退货件数 ÷ 本周售出件数”回答的是不同问题，不能混用。

## 指标契约：让口径可以复现

每个关键指标至少记录：**业务问题、统计对象、分子、分母、排除条件、时间归属、数据粒度、可切分维度、数据来源、刷新频率、责任人及样本验算结果**。这里的“契约”是团队协作约定，不是某一款软件的特殊功能。

- [[SQL与MySQL基础]] 负责从记录中筛选、连接与聚合；连接基数会改变指标。

## 选择分析方式，而不是堆方法名

| 想回答的问题 | 起点 | 需要额外警惕 |
| --- | --- | --- |
| 发生了什么 | 描述统计、分组和时间趋势 | 聚合掩盖群体差异；先看 [[概率分布与统计描述]] |
| 问题集中在哪里 | 按产品、渠道或时间拆解，检查数据质量 | 多重筛选造成样本过小或重复计数 |
| 接下来可能怎样 | 预测模型与误差回测 | 预测不是因果解释，历史关系可能变化 |
| 某项措施是否造成变化 | 对照设计、混杂因素与不确定性评估 | 相关性不能直接证明因果 |

主成分、聚类、因子分析、回归和时间序列模型只是可选工具；先明确问题、数据形态和验收标准，再决定是否需要它们。单列术语并不能构成分析方案。

## 最小验收

1. 用一句话写出用户要做的决策。
2. 写出指标口径，明确分子、分母和时间归属。
3. 写出事实表的一行代表什么，并检查连接后行数是否符合预期。
4. 用少量样本手算，与 SQL 或 Power BI 结果逐项对照。
5. 记录仍未解决的业务歧义；不要把技术实现的确定性误写成业务口径的确定性。

## 来源与边界

本文给出业务问题、指标口径和分析方法的定义流程。事实表、维度与粒度的术语参考 [Microsoft 的星型模型指南](https://learn.microsoft.com/en-us/power-bi/guidance/star-schema)；具体业务口径仍需与实际使用者确认。
