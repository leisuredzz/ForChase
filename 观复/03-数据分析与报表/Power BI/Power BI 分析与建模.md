## 背景：从问题倒推模型

报表不是把表和图拼在一起。先确定要回答的问题、指标口径和数据粒度，再决定模型关系与视觉对象。比如"按月看产品销售额"至少需要明确：销售额是否含退款、订单明细每行代表什么、产品属性按哪个时间点解释。

## 一条主线

这篇笔记按依赖顺序组织，每一步都以前一步为前提：

~~~text
1. 定粒度与口径   →  一行代表什么？指标含什么、不含什么？
2. 搭星型模型     →  事实表放数值，维度表放筛选属性，用关系连起来
3. 选计算位置     →  度量值还是计算列
4. 写表达式       →  先聚合，再在需要时用 CALCULATE 改筛选上下文
5. 验收           →  用可手算的样本核对分子和分母
~~~

跳过第 1 步直接写 DAX，是这个工具里最常见的返工原因。

## 一、模型先行：事实、维度与关系

### 1.1 事实表与维度表

**事实表**记录事件或状态及其可汇总数值；**维度表**提供筛选和分组属性。

| | 事实表 | 维度表 |
| --- | --- | --- |
| 存什么 | 可汇总的数值（金额、数量） | 描述属性（产品名、地区、日期） |
| 行数 | 多，持续增长 | 少，相对稳定 |
| 标识一行 | 先定义一致的业务粒度；可有业务键或代理键 | 用于关系的一侧键必须唯一 |
| 例子 | 订单明细、库存快照 | 产品、门店、日期 |

哪一列会成为**度量**、哪一列会成为**维度**，不取决于列名，而取决于它是连续量还是离散量：

| 变量类型 | 典型形态 | 在模型里通常的角色 |
| --- | --- | --- |
| 连续型 | 销售额、成本、利润率 | 常用作度量 |
| 连续型 | 时间、日期 | 有时用作维度（日期表就是把它当维度用） |
| 离散型 | 分类变量、次序变量、编号 | 常用作维度 |

"时间日期既是连续量又常当作维度"是这个区分的例外，也是最容易出错的一处：连续量被塞进关系当维度、离散编号被当成数值求和，都会算错。这个区分的根在 [[数据认知框架]] 的"定性数据与定量数据"一节。

### 1.2 粒度：一句话定义一行

先用一句话定义每行的粒度，例如"一个订单中的一个 SKU 明细"。

**粒度错了会发生什么**：如果事实表混合订单级和明细级数据，按 SKU 求和时订单金额会被重复计算——同一笔订单金额在多个明细行里各算一次。这类错误不会报错，只会让总额变大。

这与 [[数据仓库分层：从 ODS、DWD、DWS 到湖仓一体]] 讲的"粒度是最重要的概念"是同一件事，只是换了个工具。

### 1.3 关系：基数与筛选方向

星型模型通常让维度围绕事实表，通过键建立关系。两条规则：

1. 维度表中用于"一侧"关系的键**必须唯一**；
2. 事实表中的外键**可以重复**。

关系上的两个设置要理解清楚：

| 设置 | 含义 | 判断依据 |
| --- | --- | --- |
| 基数 | 一对多 / 多对一 / 一对一 | 由数据本身决定，不能随手改 |
| 交叉筛选方向 | 筛选往哪个方向传播 | 默认单向（维度 → 事实）；双向会带来歧义与性能代价 |

模型不必机械追求固定表数，但**每条关系都要能解释筛选如何传播**。说不清筛选从哪来、往哪去的模型，指标一定会出问题。

### 1.4 星型与雪花

星型是维度表直接连事实表；雪花是把维度表再拆细（如"产品 → 品类 → 大类"）。雪花更"规范"，但查询要多跳几次关系，报表也更容易让人看不懂层级。多数报表场景用星型，只有维度属性确实需要独立维护时才拆。

这张课程示例模型图保留了两张事实表、共享维度及各表字段的空间布局；下表把可见的关系单独列出，便于检索。`Sales` 与 `Budget` **共用** `dProduct`、`dStore`、`Calendar` 三张维度表。

这种"多个事实表共用一套维度"（一致性维度）的结构，是后面所有跨表取值的物理基础。

### 1.5 跨表取值：`RELATED` 与 `RELATEDTABLE`

模型建好之后遇到的第一个具体问题是：**事实表里的行，怎么读到维度表上的属性？**

| 函数 | 方向 | 用在什么场景 |
| --- | --- | --- |
| `RELATED(维度列)` | 从"多"端取"一"端的值 | 遍历销售明细时取产品单价、成本 |
| `RELATEDTABLE(事实表)` | 从"一"端取"多"端的行 | 在产品行上取该产品的所有销售记录 |

两个函数都**只能在行上下文中使用**（计算列、迭代函数内部），因为"当前是哪一行"必须先确定。它们要求两表之间已经存在**活动关系**，且关系的筛选方向支持这个方向的取值。

最常见的用法是把维度属性拉进事实表的行级表达式。下面的截图示例使用名为 `Product` 的维度表，与上图的 `dProduct` 是两个不同示例，不能把列名直接混用：

~~~DAX
-- 每行成本 = 该行数量 × 该产品单价（Product 是"一"端）
Total Cost = SUMX(Sales, Sales[Quantity] * RELATED('Product'[Cost]))
~~~

迭代器逐行读取 `Sales` 的行，向 `Product` 索取对应的 `Cost`，再求和。

同样一句 `RELATED` 也可以用在计算列里，此时它是逐行求值、结果落在表上——例如在 `Sales` 上建一个计算列 `related cost = RELATED('Product'[Cost])`，表里每一行都会得到该行产品对应的成本，同一个产品的多行取到同一个值。原结果截图中的前三行能说明 `related cost` 是从产品维度取来的**单位成本**，不是销售单价，也没有乘以数量：

| `ProductNum` | `Quantity` | `SalesPrice` | `related cost` |
| --- | ---: | ---: | ---: |
| `PA3006` | 2 | $38.52 | $34.82 |
| `AR1006` | 2 | $57.36 | $49.44 |
| `OS7026` | 1 | $1,169.98 | $998 |

这三行只用于解释计算列的含义；原截图其余可见行没有提供新的关系或算法规则，因此不作为第二份长期附件保存。数值来自课程截图，未与原模型逐行复算。

**该用哪个**：如果这个派生值只是给指标当中间量，放在度量值里的 `SUMX` 中即可，不落表、不占空间；只有当它需要**被筛选、被分组或用于建立关系**时才值得做成计算列。判断依据与"度量值还是计算列"完全一致，见第三节。

**优先考虑 Power Query**：如果这列只是"把 A 表的属性搬到 B 表"这种纯搬运，放在 [[Power Query 数据处理]] 的合并查询里更省事——它在数据加载阶段一次性完成，不进入 DAX 的求值路径。

### 1.6 一个事实表对同一维度有多条关系：`USERELATIONSHIP`

订单表上常同时有**下单日期、发货日期、到期日期**，它们都指向同一张日期表。但两张表之间只能有一条**活动**关系，其余必须建成非活动关系，否则筛选方向会互相打架。

`USERELATIONSHIP` 解决的就是"临时改用另一条关系来算一次"：

~~~DAX
Total Sales by Order Date = SUM(Sales[SalesAmount])

Total Sales by Ship Date =
CALCULATE(
    SUM(Sales[SalesAmount]),
    USERELATIONSHIP(Sales[ShipDateKey], 'Date'[DateKey])
)
~~~

三条约束：

1. **只能在 `CALCULATE` 内部使用**；
2. 它只**临时激活已有关系**，不会永久改变模型——非活动关系得先在模型里建好；
3. 它影响的是这一次计算的筛选传播路径，不影响其他度量值。

这类需求高频出现（订单日 vs 发货日、签约日 vs 生效日）。**已实测**：同一模型里 `Sales` 两次连到 `Date`（`Order Date` 活动、`Delivery Date` 非活动），按 2023 年筛选时，走订单日得 2,414,055.89，`USERELATIONSHIP` 改走发货日得 2,446,842.66 —— 数字确实变了，切换生效。

同时要修正一个流传的说法：同一表达式里连写两个 `USERELATIONSHIP`（先切发货日、再切回订单日）**并不报错**，结果与活动关系一致。所以「多条日期关系会报错」是有条件的——它发生在同一对表之间存在**两条活动关系**时；一活动一非活动是常规配置，DAX 会自动选活动的那条，不报错。

## 二、表达式在哪里算：行上下文与筛选上下文

这是 DAX 里最难、也最值得先弄懂的一层。

**行上下文**表示当前正在计算哪一行，常见于计算列和迭代函数。
**筛选上下文**表示当前可参与计算的行集合，来自视觉对象、切片器、关系及 DAX 过滤条件。

两者可以同时存在，不能简单地把"计算列＝行上下文、度量值＝筛选上下文"当成排他规则。

~~~DAX
销售额 = SUM(Sales[Amount])

全部产品销售额 =
CALCULATE(
    [销售额],
    REMOVEFILTERS('Product')
)
~~~

`[销售额]` 会随当前筛选上下文变化。第二个度量值在计算时移除 `Product` 表相关筛选，但仍可能受到日期等其他筛选影响。

**上下文转换**是两者之间的桥：当行上下文存在时，`CALCULATE` 会把当前行的列值转成等效的筛选条件。这是"在计算列里写 `CALCULATE` 为什么能得到按行不同的结果"的原因。

`CALCULATE` 的核心作用是**在修改后的筛选上下文中求表达式**。不能把它理解成"无条件忽略筛选器"。

## 三、先决定放哪：度量值还是计算列

这是建模阶段就要做的决定，做错了后面全是返工。

| | 度量值（Measure） | 计算列（Calculated Column） |
| --- | --- | --- |
| 何时算 | 查询时，随筛选上下文动态计算 | 刷新时，一次算好存在表里 |
| 占空间 | 无逐行存储结果，但有定义元数据和查询计算成本 | 每行存储结果，并有压缩成本 |
| 能否随切片器变化 | 能 | **不能** |
| 适合 | 比率、同比、占比等随筛选变化的指标 | 分档、拼接键、需要按它筛选或分组 |

**判断规则**：

1. 数字需要**随用户筛选变化** → 度量值；
2. 需要一个**新字段用于筛选、分组或建立关系** → 计算列；
3. 只是想把一列做个四则运算当分组依据 → 优先在 Power Query 里加，而不是 DAX 计算列。

绝大多数业务指标是第 1 类。

## 四、把多步计算拆开：`VAR`

一个比率类指标往往要算三四步（本年、去年、差额、增长率）。直接嵌套写出来，既不读者友好，也会让同一个表达式被重复求值。

`VAR` 给中间结果起名字：

~~~DAX
销售同比增长率 =
VAR 今年销售额 = CALCULATE(SUM(Sales[Amount]), 'Date'[Year] = YEAR(TODAY()))
VAR 去年销售额 = CALCULATE(SUM(Sales[Amount]), 'Date'[Year] = YEAR(TODAY()) - 1)
VAR 差额       = 今年销售额 - 去年销售额
RETURN
    DIVIDE(差额, 去年销售额)
~~~

语法是一串 `VAR 名字 = 表达式`，最后 `RETURN` 给出结果。

它带来三件事：

| 好处 | 具体表现 |
| --- | --- |
| 可读 | 每个步骤有名字，读代码的人不用在嵌套括号里找逻辑 |
| 不重复求值 | 同一个中间结果被引用多次时，引擎只需算一次 |
| 可排错 | 把 `RETURN` 暂时改成某个变量，就能看到中间值是多少 |

**一个容易踩的点**（已实测）：变量在**定义那一行**的上下文里求值一次，之后引用的是那个已经算好的结果。所以不要指望把变量放进 `CALCULATE` 里"重新算一遍"——需要随上下文变化的东西，要写成度量值或表达式，不能预先存进变量。

实测对照（同一模型：全局销售额 7,305,939.03，Computers 类 2,785,879.73）：

| 写法 | 结果 |
| --- | --- |
| `VAR x = CALCULATE([Sales Amount], ALL(Product)) RETURN CALCULATE(x, Product[Category] = "Computers")` | 7,305,939.03（**没变**） |
| `CALCULATE([Sales Amount], ALL(Product), Product[Category] = "Computers")` | 2,785,879.73（筛选生效） |

两行的差别只在「筛选发生在变量之前还是之后」：变量已经把值定死了，后面再给筛选也改不动它。

`VAR` 还顺带解决了老写法里的作用域问题：需要记住"外层那一行"的值时，用 `VAR` 命名比用 `EARLIER` 清楚得多（见 6.4）。

## 五、聚合、迭代、计数与排名

### 5.1 `SUM` 与 `SUMX` 的差别

`SUM` 只能对**一个已有的列**求和。但很多指标的行级表达式并不存在于表里，例如"每行金额 = 数量 × 单价"：

~~~DAX
-- 不行：表里没有"金额"这一列
SUM(Sales[Quantity] * Sales[UnitPrice])

-- 正确：先逐行算表达式，再求和
SUMX(Sales, Sales[Quantity] * Sales[UnitPrice])
~~~

`SUMX` / `AVERAGEX` / `MAXX` / `MINX` / `COUNTX` 是**迭代函数**：遍历表 → 对每行求表达式（建立行上下文）→ 再聚合。这正是行上下文存在的理由。

### 5.2 什么时候必须用迭代

| 场景 | 用什么 |
| --- | --- |
| 直接对现成列求和 | `SUM` |
| 需要先算"数量 × 单价"这类行级表达式再汇总 | `SUMX` |
| 要算"平均每笔订单金额"（而不是平均单价） | `AVERAGEX(Sales, Sales[Qty] * Sales[Price])` |
| 要算有多少个非空结果（而不是非空列） | `COUNTX` |

**常见错误**：用 `AVERAGE(单价)` 当"平均客单价"。前者是价格的平均，后者是"总金额 ÷ 单数"，两者在单据金额不等时会明显不同。这与 [[概率分布与统计描述]] 的"加权平均 vs 简单平均"是同一个陷阱。

### 5.3 计数：`COUNTROWS` 与 `DISTINCTCOUNT`

数"有多少"是最常见的需求，也是最容易答错的：

| 问的是什么 | 用哪个 | 例子 |
| --- | --- | --- |
| 有几行（几笔交易、几条明细） | `COUNTROWS(表)` | 订单明细 12,000 行 → 12,000 |
| 有几个不重复的值（几个客户、几个SKU） | `DISTINCTCOUNT(列)` | 同一批明细里只有 800 个不同客户 → 800 |

两者在明细表上**必然不相等**，而且差多少完全取决于业务：一个客户下 100 单，行数 100、去重客户数 1。把"客户数"写成 `COUNTROWS` 会得到一个随下单频次变化、无法解释的数字。

`COUNTROWS` 还有一个用法是配 `FILTER` 数

**一处容易看错的地方**（已实测）：`COUNTROWS` 数一张**空表**时返回的是**空白，不是 0**。`COUNTROWS(FILTER(...))` 在没有任何行满足条件时结果为空，`ISBLANK` 为真，参与运算要先 `+ 0` 或 `COALESCE`。它和「数出来是零」在报表上长得像，在算术里不是一回事。"满足条件的行数"，见 6.4。

### 5.4 比率不要直接除：`DIVIDE`

只要分母可能为 0 或空，直接写 `A / B` 就会得到错误值。`DIVIDE` 是安全除法：

~~~DAX
客单价 = DIVIDE([总销售额], [订单数])
~~~

第三参数可指定"分母为空时返回什么"，缺省返回空值。对"占比、同比、人均、单均"这类指标，用它比写 `IF(分母=0, ..., A/B)` 更短也更少出错。

**`DIVIDE` 与 `/` 不是同一个东西**（已实测）：`DIVIDE(1, 0)` 与 `DIVIDE(0, 0)` 都返回空白，`DIVIDE(1, 0, -1)` 返回 −1；但直接写 `1 / 0` 得到的是 **`inf`（无穷大）**，不是空白。也就是说「除以零」在 DAX 里不是报错，而是一个会继续参与后续加减与汇总的值。看到比率字段冒出一个 `inf`，就是这里漏用了 `DIVIDE`。

### 5.5 统计聚合：`MEDIAN`、`STDEV`、`VAR`

DAX 里可以直接算描述统计量，不需要把数据导出去：

| 函数 | 算什么 | 与 [[概率分布与统计描述]] 的对应 |
| --- | --- | --- |
| `MEDIAN(列)` | 中位数 | 集中趋势中的稳健代表，不受极端值拉动 |
| `STDEV.S(列)` / `STDEV.P(列)` | 标准差（样本 / 总体） | 离散程度；`.S` 除以 n−1，`.P` 除以 n |
| `VAR.S(列)` / `VAR.P(列)` | 方差（样本 / 总体） | 标准差的平方 |

**`.S` 与 `.P` 的选择**（这是本库唯一一处把统计概念与工具接起来的地方）：如果这列数据是**总体本身**（例如全体员工数、全部订单），用 `.P`；如果它是**从更大总体中抽出的样本**（例如抽检的 500 单），用 `.S`。

数据量大时两者差别很小，但口径要说清——报表里同一个指标混用 `.S` 和 `.P`，会让两份报表的"波动"数字对不上。

### 5.6 排名与前 N：`RANKX` 与 `TOPN`

| 需求 | 用哪个 | 要点 |
| --- | --- | --- |
| 给每个产品一个排名序号 | `RANKX(表, 表达式)` | 要按名次排的字段必须**注意并列**的处理 |
| 只取前 N 名 | `TOPN(N, 表, 表达式, DESC)` | 返回的是**表**，要再用 `CALCULATE` 或其他聚合把它算成值 |

~~~DAX
产品销售额排名 = RANKX(ALL('Product'[ProductName]), [销售额])
前 5 名客户销售额 =
VAR 前五名 = TOPN(5, ALL('Customer'[CustomerName]), [销售额], DESC)
RETURN CALCULATE([销售额], 前五名)
~~~

两个坑：一是**排名要在哪个集合里排**必须写清楚——`ALL` 是"全部产品"，不加 `ALL` 则是在当前筛选（比如当前品类）内排名，结果完全不同；二是**并列的处理方式**会让名次不连续（两个第 1 名之后直接是第 3 名），对外报表要事先决定怎么显示。

显式指定并列规则的结果**已实测**。用 `{A:10, B:20, C:20, D:30}` 按值降序排名，第五参数分别取 `Dense` 与 `Skip`：

| 名称 | 值 | `Dense` | `Skip` |
| --- | --- | --- | --- |
| D | 30 | 1 | 1 |
| B | 20 | 2 | 2 |
| C | 20 | 2 | 2 |
| A | 10 | **3** | **4** |

并列的两行名次相同；差别只在并列之后——`Dense` 接着数 3，`Skip` 跳到 4。所以「两个第 1 名之后直接是第 3 名」只对 `Skip` 成立。**省略第五参数时默认 `Skip`**，依据是 [Microsoft 的 `RANKX` 文档](https://learn.microsoft.com/zh-cn/dax/rankx-function-dax)；上表只实测了显式传参，不能把默认值也写成已实测。

## 六、`CALCULATE`：在修改后的筛选上下文中求值

### 6.1 它在做什么

~~~DAX
CALCULATE(<expression>[, <filter1> [, <filter2> [, …]]])
~~~

它接收一个表达式和若干筛选条件，**在改过的筛选上下文里求这个表达式的值**。它能覆盖、增加或移除现有筛选器，从而创造一个全新的计算环境。

需要清楚的两点：

1. **返回一个标量值**，不是表。需要在修改后的筛选上下文中返回表，可用 `CALCULATETABLE`；`FILTER` 则逐行筛选表表达式。
2. 这个值可以用在**度量值**里，也可以用在**计算列**里。用在计算列时会为每行分别计算——这正是上下文转换发生的场合。

### 6.2 筛选器参数

| 形式 | 例子 | 效果 |
| --- | --- | --- |
| 布尔表达式 | `Sales[Country] = "China"` | 给该列加筛选 |
| 表筛选 | `FILTER(ALL(Sales), Sales[Amount] > 200)` | 用整张虚拟表替换筛选 |
| 筛选器修改函数 | `REMOVEFILTERS('Product')` | 移除某表/列的筛选 |

### 6.3 默认行为是"替换"而不是"叠加"

这一点经常被搞反：**`CALCULATE` 的筛选器参数会替换同一列上已有的筛选器**，而不是与它取交集。想让两者取交集，用 `KEEPFILTERS`（见 7.5）。

### 6.4 `FILTER`：它返回表，而且代价不低

`FILTER(表, 条件)` 逐行扫描表、保留条件为真的行，**返回一张表**（不是值）。这是它与 `CALCULATE` 的分工：`CALCULATE` 算值，`FILTER` 造表。

它最常见的用法确实是当 `CALCULATE` 的筛选器参数：

~~~DAX
高销售额总和 =
CALCULATE(
    SUM('销售表'[SaleAmount]),
    FILTER(ALL('销售表'[SaleAmount]), '销售表'[SaleAmount] > 200)
)
~~~

但**代价在于"逐行扫描"**。如果条件只是"某列等于/大于某个值"，那么直接写布尔表达式更快：

~~~DAX
高销售额总和 =
CALCULATE(SUM('销售表'[SaleAmount]), '销售表'[SaleAmount] > 200)
~~~

判断规则：**能用布尔表达式或筛选器修改函数表达的，就不要用 `FILTER` 包一层**。真正需要 `FILTER` 的是这两种情况——条件要引用**度量值**（布尔筛选器做不到），或者需要在筛选表本身逐行求值。

`FILTER` 还常与"记住外层行"的需求一起出现。老写法用 `EARLIER` 引用外层行上下文：

~~~DAX
'销售表'[ProductID] = EARLIER('销售表'[ProductID])
~~~

现代写法改成先取变量再引用，`VAR` 只求值一次、意图也更直白：

~~~DAX
VAR 当前产品 = '销售表'[ProductID]
...
FILTER(ALL('销售表'), '销售表'[ProductID] = 当前产品)
~~~

两者语义等价，新代码优先 `VAR`。

> 来源里的这个示例曾给出错误的结果表：产品 A 的三次销售为 100／150／120，均值是 370÷3 ≈ **123.33**，不是 136.7。原文已随归档删除，无法再逐字对照它的公式；但「三次销售之和为 370」这一点已在本机 DAX 引擎里用 `SUMX(FILTER(T, [产品] = EARLIER([产品])), [金额])` 独立复现（结果正是 370），所以 136.7 无论按哪种算法取平均都不成立。

## 七、筛选器修改函数族：按"移除什么"排列

这一族函数最容易记混。按"移除范围从大到小"排，关系就清楚了。

### 7.1 一览表

| 函数 | 移除什么 | 典型用途 |
| --- | --- | --- |
| `REMOVEFILTERS(表)` / `ALL(表)` | 该表所有列的筛选 | 算占总额百分比 |
| `ALL(列)` | 仅该列的筛选 | 保留其他维度、只看这一维 |
| `ALLEXCEPT(表, 列A, 列B)` | 除列 A、列 B 外，该表其余列的筛选 | 按类别汇总时忽略地区筛选 |
| `ALLSELECTED()` | 视觉对象内部的筛选，但保留用户主动选择 | 动态响应切片器的"占所选百分比" |
| `KEEPFILTERS(条件)` | 不移除，改为**取交集** | 让筛选叠加而不是替换 |

### 7.2 `REMOVEFILTERS` 与 `ALL`

两者功能等价，`REMOVEFILTERS` 语义更清晰：

| 表达式 | 说明 |
| --- | --- |
| `ALL(Products)` | 移除 `Products` 表上所有列的筛选（字面意思是"返回所有值的表"） |
| `REMOVEFILTERS(Products)` | 同上，但意图直接写成"我要移除筛选" |

写新度量值时优先用 `REMOVEFILTERS`——读代码的人不用猜你是要一张表还是要去筛选。

用一组可手算的数据可以看清效果（4 行销售合计 700）：

| 度量值 | 在 Region 切片器选中 North 时返回 |
| --- | --- |
| `CALCULATE(SUM(...), ALL(Sales))` | 700（完全忽略筛选） |
| `CALCULATE(SUM(...), ALLEXCEPT(Sales, Sales[Category]))` | 按类别分别为 300 与 400（忽略 Region，保留 Category） |
| `CALCULATE(SUM(...), ALLSELECTED(Sales))` | 250（尊重用户选择的 North） |

上面这组数字是构造的小样本。同样的关系已在真实模型上核对过：8 个产品类别各自一行时，`ALLEXCEPT(Product, Product[Category])` 的返回值与**该行自身的值完全相等**（因为它只保留类别筛选，正是当前行的上下文），而 `ALLSELECTED(Product[Category])` 在**每一行**都等于全局值 7,305,939.03；8 行相加也正好等于全局值。

### 7.3 `ALLEXCEPT`

`ALLEXCEPT(Sales, Sales[Category])` 只保留 `Category` 的筛选上下文，移除该表其他所有列的筛选。适用于"按某维度分组时，忽略其他维度干扰"。

### 7.4 `ALLSELECTED`

`ALLSELECTED` 保留的上下文比"保留所有切片器选择"**更复杂**，具体结果取决于查询内外的筛选。它在视觉总计、占比场景中常用。已实测的一条：在 `SUMMARIZECOLUMNS(Product[Category], ...)` 里，`CALCULATE([Sales Amount], ALLSELECTED(Product[Category]))` 对**每一行**都返回全局值，因为它保留了查询外部的筛选、去掉了当前行自己的筛选。但这只是一个上下文下的结果，"永远保留切片器、移除其他筛选"。

### 7.5 `KEEPFILTERS`

默认情况下 `CALCULATE` 的筛选器参数替换同列的现有筛选。`KEEPFILTERS` 改变这个行为：**把现有筛选与参数中的筛选取交集**。

~~~text
CALCULATE 的筛选器参数：替换当前上下文
KEEPFILTERS 的参数：       添加到当前上下文（取交集）
~~~

后果很直观。下面这组对照可以直接看清两版写法的差别（`Sales Innovative = CALCULATE([Total Sales], …)`，矩阵行是 `Product[ProductType]`）：

| 矩阵行 | Total Sales | 不加 `KEEPFILTERS` 的 Sales Innovative | 加了 `KEEPFILTERS` 的 Sales Innovative |
| --- | --- | --- | --- |
| Oct 2022（合计行） | 1,384,544 | 131,724 | 131,724 |
| Innovative | 131,724 | 131,724 | 131,724 |
| Standard | 1,252,821 | **131,724** | **（空）** |
| Total | 1,384,544 | 131,724 | 131,724 |

关键在 `Standard` 那一行：不加 `KEEPFILTERS` 时它照样显示 131,724，也就是**把 Innovative 的数字贴到了 Standard 行上**——因为 `CALCULATE` 的筛选器覆盖了视觉对象给它加的 `ProductType` 筛选。症状是整个 Innovative 列**拆不开也加不回去**：三行相加得 394,172，而合计行只有 131,724。

加上 `KEEPFILTERS` 之后，条件与视觉对象的筛选**取交集**：`Standard` 行交集为空，所以显示空；`Innovative` 行交集就是它自己，值不变。这时列才拆得开、加得回。

**判据**：当一个度量值要在**按同一列分组的矩阵里**再对那一列下条件（典型是「按产品类型分行，同时只想看创新款」），几乎一定要加 `KEEPFILTERS`；否则每一行都会显示同一个值。

顺带一条可核对的规律：这类「每行都相同」的错误**不会报错**，只会让列加不回合计。所以验收时除了看单个格子，也要看**明细行相加是否等于合计行**。

## 八、占比的分母是什么

"占比"没有唯一正确分母：可能是当前页合计、筛选后的可见产品合计，或全库合计。**先写出业务定义，再选函数**。

| 分母的含义 | 用哪个 |
| --- | --- |
| 全部数据合计（忽略一切筛选） | `REMOVEFILTERS` / `ALL` |
| 用户当前所选范围内的合计 | `ALLSELECTED` |
| 保持其他维度筛选，只放开这一维 | `ALL(列)` |

分母口径不一致是两张报表对不上的最常见原因。这与 [[数据治理建设笔记]] 里"指标口径"一节讲的是同一个问题。

## 九、时间智能与日期表

### 9.1 日期表是前提

时间智能函数（同比、YTD、环比）依赖一张**独立的日期表**，它应当：

- 覆盖分析范围内的**连续**日期，一天不缺；
- 有一个适合作为日期键的列（通常是 `Date`，不是文本）；
- 与事实表建立关系。

若使用经典时间智能函数，Power BI 对标记为日期表的日期列会检查**唯一、非空、连续**等条件。标记日期表时若该列不满足这些条件，校验不会通过；即使未标记，日期覆盖范围也要按实际时间智能计算核对。

事实表里的日期列**不能**直接拿来当时间智能的日期列：订单稀疏时日期不连续，函数会静默算错。

### 9.2 造一张日期表

最短的写法是用 `CALENDAR` 生成单列日期，再补上要用于分组的属性列：

~~~DAX
日期表 = CALENDAR(DATE(2025, 1, 1), DATE(2025, 12, 31))
~~~

`CALENDAR(开始, 结束)` 的**两个参数都必须是标量**（单个日期值），不能直接传列。要按数据实际范围动态生成，先用变量把范围取成标量：

~~~DAX
日期表 =
VAR 起 = MINX(ALL(Sales), Sales[OrderDate])
VAR 止 = MAXX(ALL(Sales), Sales[OrderDate])
RETURN CALENDAR(起, 止)
~~~

补属性列时 `EOMONTH` 很常用，它返回某月最后一天：

| 表达式 | 结果 |
| --- | --- |
| `EOMONTH(DATE(2024,2,5), 0)` | 2024-02-29（闰年二月） |
| `EOMONTH(DATE(2023,5,15), 1)` | 2023-06-30（下月月末） |
| `EOMONTH(DATE(2024,2,5), -1)` | 2024-01-31（上月月末） |

（已在引擎里复核：`EOMONTH(DATE(2024,2,10), 0)` → 2024-02-29，`EOMONTH(DATE(2024,2,10), 1)` → 2024-03-31，`EDATE(DATE(2024,3,31), -1)` → 2024-02-29。顺带一条：`DATE(2023, 13, 1)` 不报错，得 2024-01-01，月份溢出会自动进位到下一年。）

> **已实测**：`CALENDAR(DATE(2024,2,1), DATE(2024,3,31))` 返回 60 行，去重后仍是 60 行，首行 2024-02-01、末行 2024-03-31 —— **连续、唯一、非空三条同时成立**（2024 年 2 月 29 天 + 3 月 31 天 = 60，与闰年吻合）。所以「拿它当日期表合不合规」这一层不必担心；**仍需自己补**的是年／季／月这些用于分组的属性列，以及给月份名之类的文本列设置按数字列排序。`CALENDAR` 生成的是单一日期列；用它当日期表是否满足"连续、唯一、非空"，以及是否需要额外补年/季/月列与排序，要在实际模型里按当前版本核对。来源材料这一节本身存在矛盾（标为"错误写法"的示例又被注为"新版本可用"），**没有采信**。

### 9.3 时间智能三件套

日期表建好、关系接上之后，同比与累计就是固定句式：

| 需求 | 函数 | 写法 |
| --- | --- | --- |
| 去年同期 | `SAMEPERIODLASTYEAR` | `CALCULATE([销售额], SAMEPERIODLASTYEAR('日期表'[Date]))` |
| 平移若干时间单位 | `DATEADD` | `CALCULATE([销售额], DATEADD('日期表'[Date], -3, MONTH))` |
| 年初至今累计 | `TOTALYTD` | `TOTALYTD([销售额], '日期表'[Date])` |

- `SAMEPERIODLASTYEAR` 返回的是**表**（去年同期的日期集合），所以它只能当 `CALCULATE` 的筛选器参数。
- `DATEADD` 的第三个参数决定平移单位（`YEAR` / `QUARTER` / `MONTH` / `DAY`）；正数向未来、负数向过去。
- `TOTALYTD` 直接返回**值**，是"从年初累计到当前日期"的快捷写法，第四个参数可指定财年结束日（如 `"06-30"` 表示 6 月底结账）。

用一组 5 个月的月度销售额（100／150／200／120／180）可以手算核对 YTD 的语义：累计应为 **100／250／450／570／750**（已复核）。

> **已实测**（真实模型 2023 年，日历年销售额 2,414,055.89）：
> - `TOTALYTD` 输出的逐月累计与逐月相加**严格一致**；
> - `SAMEPERIODLASTYEAR` 每月返回的正是上一年同月的值；
> - `TOTALYTD` 第四参数传 `"6/30"` 后累计在 **7 月重置**（7 月 YTD 只等于 7 月月值），财年口径确实生效；
> - `RELATED('Date'[Year])` 在「一个活动、一个非活动」的关系下**不报错**，会自动使用活动关系，所以「多日期关系报错」并不是这种配置的后果。
> - 另外，2023 年 12 月的 `TOTALYTD` 累计值 2,414,055.89 与上面 USERELATIONSHIP 一节单独算出的「2023 年按订单日合计」完全相同，两条独立路径互相印证。

### 9.4 新旧方式要求不同

按当前模型和官方文档选择，不要照抄旧教程。日期表的生成方式与时间智能函数的可用条件在不同版本间有变化；上面那些数字是本机这个版本的实测结果，换版本或换模型时仍应先用小样本核对日期边界（月初、月末、跨年、闰年）。

## 十、表函数与辅助表

### 10.1 `SUMMARIZE` 与 `SUMMARIZECOLUMNS`

两者都是"按若干列分组、再算几个聚合"的造表函数。微软的官方建议很明确：

> **新代码优先使用 `SUMMARIZECOLUMNS`**，只在需要兼容旧版本或特定上下文时使用 `SUMMARIZE`。

差别在于写法约束：

| | `SUMMARIZE` | `SUMMARIZECOLUMNS` |
| --- | --- | --- |
| 引用度量值 | 需要额外包装 `CALCULATE` | 可直接用 |
| 筛选器 | 作为参数的表表达式 | 可用 `TREATAS`、`FILTER`、布尔条件 |
| 未分组的基础表列 | 可能产生"歧义列" | 不能直接引用 |

这条只需记住结论：**新建汇总表先写 `SUMMARIZECOLUMNS`**。

### 10.2 什么时候需要辅助表

有些视觉需求本身就需要一张"没有业务含义"的表：连续数字轴、月份清单、可选指标清单、价格区间。

~~~DAX
-- 生成 1 到 N 的连续整数序列，[Value] 是 GENERATESERIES 自动生成的列名
数字轴 = SELECTCOLUMNS(GENERATESERIES(1, 12), "X", [Value])
~~~

这类表通常是**计算表**，进模型后**不要与其他表建立关系**——它的作用只是提供坐标或选项，不是提供筛选。具体用法见 [[Power BI 报表设计与性能]] 里的动态度量选择器与累计分布图。

生成辅助表的手法很多（`GENERATESERIES`、`CALENDAR`、手写常量表、`SELECTCOLUMNS` 改名），属于"要用时查官方文档"的工具语法，不在本文展开。

## 十一、方案：最小验收表

发布报表前，选一个可以手工核对的小样本，逐项核对：

1. 每张事实表的行粒度和主键／业务键。
2. 维度"一侧"键是否唯一，是否有未匹配的事实行。
3. 筛选器变化时，度量值分子和分母分别怎样变化。
4. 重复运行、刷新与日期边界是否改变结果。

第 3 条最容易被跳过，也最容易发现问题：**把切片器逐个点一遍，看分母有没有跟着变**。

---

## 十二、常见误区

1. **先做图再想口径**——图做得漂亮，数字没人敢用。
2. **粒度没定义就开始建关系**——订单金额被明细行重复计算。
3. **把 `CALCULATE` 当成"忽略所有筛选"**——它是替换指定列的筛选，不是清空。
4. **误以为 `CALCULATE` 的筛选是叠加**——默认是替换，叠加要用 `KEEPFILTERS`。
5. **用 `AVERAGE(单价)` 代替平均客单价**——简单平均与加权平均的差别。
6. **把 `ALLSELECTED` 当成「永远保留切片器」**——它保留的上下文比这复杂，已实测的只是其中一种上下文。
7. **计算列用于需要随筛选变化的值**——计算列在刷新时算好，不会随切片器变。
8. **关系设成双向"以防万一"**——带来歧义与性能代价，缺依据就不要开。
9. **日期表不连续**——时间智能静默出错。
10. **只看总数不看分母**——占比错了比数值错了更隐蔽。
11. **把"客户数"写成 `COUNTROWS`**——那是行数，不是去重人数，且会随下单频次变化。
12. **比率直接相除**——分母为 0 时得到错误值，应该用 `DIVIDE`。
13. **用 `FILTER` 包住整表做本可用布尔筛选器的条件**——逐行扫描的代价被白白付出。
14. **以为变量会随上下文重算**——`VAR` 在定义处求值一次，之后的引用不再变化。
15. **在深层嵌套里靠 `EARLIER` 猜作用域**——现代写法优先用 `VAR` 记住外层值。

16. **以为除以零会报错**——`1 / 0` 返回 `inf` 而不是空白，它会继续参与后面的加减；要空白得用 `DIVIDE`。
17. **把 `COUNTROWS` 的空结果当成 0**——空表上它返回空白，`+ 0` 之后才是个可运算的零。

## 现阶段认知

Power BI 的难点不是记住更多函数，而是把"**当前有哪些行参与计算**"说清楚。

按这个标准重新看上面所有内容，会发现它们在讲同一件事的不同侧面：

- 行上下文与筛选上下文，是"哪些行"的两种来源；
- `CALCULATE` 与筛选器函数族，是"怎样改哪些行"的工具；
- 度量值与计算列的区别，是"什么时候算哪些行"；
- 关系与基数，是"筛选怎样传播到哪些行"；
- `VAR` 与 `DIVIDE` 这类函数不改变"哪些行"，只让表达更清楚、更不容易出错。

所以遇到一个算不对的指标，值得先问的不是"该用哪个函数"，而是"**这一行参与了没有、被什么筛掉了**"。把这句话答清楚，函数自然就选定了。
