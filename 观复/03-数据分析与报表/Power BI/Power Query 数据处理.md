# Power Query 数据处理

> **先修**：[[数据认知框架]]（字段、类型与粒度）。模型与度量见 [[Power BI 分析与建模]]。
> **定位**：Power BI 工作流**进模型之前**的那一层——取数、清洗、改类型、合并、分组。模型建好之后的建模、度量与报表，分别在 [[Power BI 分析与建模]] 与 [[Power BI 报表设计与性能]]。
> **核验状态**：文档核对——本机装有 Power BI Desktop（含 Power Query），但**没有找到可脚本调用的 M 求值器**（未安装 Power Query SDK，桌面版也不提供命令行求值入口）。因此 M 的语义**仍未在本机求值验证**，依微软官方 M 语言规范整理——这一点与 DAX 不同，DAX 已经实测过。标「补充」的是整理时补入的基础内容，不属于原始来源材料。详见 [[知识库质量审计]]。

## 背景：模型不会自己变干净

数据源给出来的东西通常不能直接进模型：日期是文本、金额列里混着空字符串、一个指标的逻辑分散在两张表、几十列里只用到六列。

在 Power BI 里，这段"进模型之前的活"有专门的一层——**Power Query**。它用一门叫 **M** 的语言描述每一步转换，结果交给模型。

把这一层单独看懂，有两个实际好处：一是知道哪些坑在建模阶段就消失了，不用等到写 DAX 才发现；二是遇到"刷新很慢""数字对不上"时，知道该查哪一段。

## 问题：这段处理到底该放在哪一层

同一件事（例如"加一列税后金额"）往往有好几个地方可以写。放错位置，代价是长期的。

| 层 | 适合做什么 | 不适合做什么 |
| --- | --- | --- |
| 数据源 / SQL | 只取需要的行列；能在源头算的聚合尽量在源头算 | 源系统不能改的时候 |
| **Power Query** | 清洗、改类型、去重、合并/追加、分组、加派生列 | 需要随切片器变化的计算 |
| DAX 计算列 | 需要参与关系或筛选、且刷新时定值即可的新字段 | 逐行落表占空间；多数派生列本可在 Power Query 做 |
| DAX 度量值 | 随筛选、随时间动态计算的指标 | 不能用于筛选、分组或建立关系 |

判断规则（**补充**，属经验判据）：

1. 结果**不随用户筛选变化**、且**进模型前就该定型** → Power Query；
2. 目的是让某列**能筛选、能分组、能建关系** → 优先 Power Query，其次 DAX 计算列；
3. 需要**随切片器、随日期变化** → 只能写度量值。

这三条与 [[Power BI 分析与建模]] 第三节的"度量值还是计算列"是同一套判断，只是多加了最前面的一层。

## 方案：一个查询就是一串有名字的步骤

M 查询的基本形状是 `let ... in`：`let` 里面给每一步起名，后一步引用前一步；`in` 返回最后那一步。

~~~text
let
    源      = Excel.Workbook(File.Contents("D:\data\sales.xlsx")),
    订单    = 源{[Item="订单", Kind="Table"]}[Data],
    改类型  = Table.TransformColumnTypes(订单, {{"OrderDate", type date}, {"Amount", type number}}),
    去空行  = Table.SelectRows(改类型, each [Amount] <> null)
in
    去空行
~~~

三个最常用的表函数（**补充**）：

| 函数 | 做什么 | 关键点 |
| --- | --- | --- |
| `Table.SelectRows(表, 条件)` | 按条件保留行 | 条件是一个"逐行判断"的函数，见下节 |
| `Table.AddColumn(表, "列名", 表达式, 类型)` | 加一列 | 表达式按当前行计算 |
| `Table.TransformColumnTypes(表, {{"列", type}, …})` | 改数据类型 | 类型不改对，后面的聚合和日期函数就会出错 |

**步骤是值，不是命令**（**补充**）：上面每一步都产生**一张新表**，不会就地修改原来的表。所以步骤可以随意改名、调序、回退——这也是"查询出错时先看是哪一步开始不对"能成立的原因。

## 原理一：`each` 与 `(x) =>` 是同一个东西

M 里到处出现 `each`，看起来像个关键字，其实它只是**写函数的简写**。

微软 M 语言规范的原文是：

> The *each-expression* is a syntactic shorthand for declaring untyped functions taking a single parameter named `_` (underscore).

翻译过来：**`each` 是"声明一个只接受一个参数、参数名叫 `_`（下划线）的函数"的语法简写**。规范同时给出了等价对照：

| 简写 | 完全等价的写法 |
| --- | --- |
| `each _ + 1` | `(_) => _ + 1` |
| `each [A]` | `(_) => _[A]` |
| `Table.SelectRows(aTable, each [Weight] > 12)` | `Table.SelectRows(aTable, (_) => _[Weight] > 12)` |

于是两件事就清楚了：

1. **`[列名]` 是 `_[列名]` 的简写**。`_` 就是"当前这一行"，在 M 里它是一个**记录（record）**，方括号就是取字段。
2. 所以 `each [金额] > 100` 的完整意思是"给我一个函数，它取参数 `_` 的 `金额` 字段，判断是否大于 100"。表函数把每一行依次传进去，就完成了逐行处理。

一个例外要记住：**列表（list）里 `_` 是当前元素本身，不是记录**，所以 `List.Transform({1,2,3}, each _ * 10)` 里不能写 `[字段]`。

## 原理二：嵌套时谁遮蔽谁

把 `each` 嵌在 `each` 里，是 Power Query 里最容易讲错的一处。

每一层 `each` 都各自引入一个自己的 `_`，**内层的 `_` 遮蔽外层的 `_`**。这意味着下面这种写法**不是错的**：

~~~text
Table.AddColumn(源, "高金额订单", each Table.SelectRows(源, each [金额] > 100))
~~~

内层的 `_[金额]` 指的是内层正在筛选的那一行，语义是明确的。

真正的问题在别处：**内层里已经拿不到外层那一行**——因为 `_` 被遮蔽了。想在外层行里读一个值去和内层比较时，必须给外层参数起个名字：

~~~text
Table.AddColumn(源, "同行订单", (外行) => Table.SelectRows(源, each [金额] = 外行[金额]))
~~~

> **修正记录**：原始材料把第一种写法判为"错误"，理由是"两个 `each` 都试图使用 `_`，Power Query 无法区分"。按 M 规范的作用域规则（函数体引用它被定义时所在环境中的变量，内层参数遮蔽同名外层参数），内层不存在歧义。**真正需要 `(x) =>` 的原因是"要引用外层值"，而不是"内层写法不合法"**。M 部分仍未在本机求值——桌面版的 Power Query 无法从命令行驱动——本结论依 M 规范的作用域规则与官方文档表述。若要把它变成机器可验证的结论，需要先装 Power Query SDK 的 `pqtest`。

可用判据：

| 场景 | 写法 |
| --- | --- |
| 单层，条件只用到当前行 | `each`（更短，也更常见） |
| 嵌套，内层只关心自己的行 | 内层仍可用 `each` |
| 嵌套，内层要引用外层行 | 外层必须用 `(x) =>` 命名 |

## 常见混淆：Power Query 用的是 M，不执行 DAX

| | Power Query | 模型 |
| --- | --- | --- |
| 语言 | **M** | **DAX** |
| 处理对象 | 表、列、行，在数据加载阶段 | 已进模型的表，在查询阶段 |
| 典型工作 | 改类型、合并、分组、加派生列 | 度量值、计算列、时间智能 |

由此有两处常见误解：

- **`EVALUATE` 不是 Power Query 的语法**。它是 DAX 的查询语句，用在 DAX Studio、SSAS 等地方。
  > **修正记录**：原始材料称 `EVALUATE` "常用于 Power Query 中的 DAX 查询"，语言分工说错了。
- **DAX 计算列不等于 Power Query 派生列**。前者在刷新时逐行落表，后者在加载时算完就不占模型的求值路径。能用后者时优先用后者。

一句判断口诀（**补充**）：**洗数据用 M，算指标用 DAX。**

## 现阶段认知

Power Query 的价值不在"多会几个函数"，而在**把不清楚的数据挡在模型外面**。

判断一个转换该不该放在这一层，问一句话就够：**它会不会随用户的操作变化？** 不会，就尽量在这儿做完；会，就一定属于模型里的度量值。

同理，遇到"数字对不上"时，排查顺序应当是从外往里：先看视觉对象的筛选，再看度量值，再看关系，最后才怀疑 Power Query——因为它已经定型，是整条链路里最不会变的一段。
