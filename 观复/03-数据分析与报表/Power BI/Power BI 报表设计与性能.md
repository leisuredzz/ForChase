# Power BI 报表设计与性能

> **先修**：[[Power BI 分析与建模]]。
> **核验状态**：已实测——本机装有 Power BI Desktop 2.148.1477.0，下面的选择器模式已在该版本的本地引擎上实测，结果见本节末尾；性能相关的部分属于方法，不产生可核对的数字。详见 [[知识库质量审计]]。

## 背景：报表服务于一个决定

一页报表先回答“谁要据此决定什么”，再放指标和图。相同的销售额，对管理者可能是趋势与异常，对运营人员可能是 SKU 明细和处理入口。先写出用户、决策、时间范围、数据刷新频率与口径，避免图表堆砌。

## 问题：页面看得懂，数字可信吗

设计与验收分成三层：

1. **数字**：从源表取可手算样本，核对筛选前后指标和汇总关系。模型检查参见 [[Power BI 分析与建模]]。
2. **表达**：标题说明所示范围，单位、时间粒度和颜色含义保持一致；不要只用颜色传达异常。
3. **行动**：异常出现后，用户能否定位维度和记录，知道下一步找谁处理。

“最漂亮”的图不一定最有用。若一个表格能更快显示差异和明细，就无需为了视觉新颖改成复杂图形。

## 方案：从最小页面开始

- 首页只放关键指标、时间趋势与异常入口。明细放到钻取页或独立页面，不在同一页复制相同数字。
- 用统一的度量值和格式定义指标；显示文件夹可以帮助管理度量值，但不改变计算结果。
- 对有意义的图片和视觉对象写替代文本，检查键盘焦点顺序、对比度与色觉可辨性。
- 工具提示用于补充信息，不作为唯一承载重要结论的地方。

## 表达：让用户能切换与比较

### 动态度量选择器

需求很常见：同一张折线图，用户想自己切换看销售额、利润、成本还是数量。

做法是**三样东西配一套**：

1. 一张**参数表**，只有一列，内容是可选的度量值名称（`Margin`、`Sales Amount`、`Total Cost`、`Total Quantity`）。它不含业务数据，只提供选项。
2. 把这一列放进切片器。
3. 写一个"返回所选度量值"的度量值：

~~~DAX
Metric Value =
SWITCH(
    SELECTEDVALUE(Metric[Measure]),
    "Margin", [Margin],
    "Sales Amount", [Sales Amount],
    "Total Cost", [Total Cost],
    "Total Quantity", [Total Quantity],
    ERROR("Measure not selected in Metric[Measure]")
)
~~~

三个部件各自解决一个问题：

| 部件 | 作用 | 不加会怎样 |
| --- | --- | --- |
| `SELECTEDVALUE(列)` | 只在**恰好选中一个值**时返回它，多选或未选返回空 | 度量值里不能直接引用列；`VALUES` 返回的是表，不能当 `SWITCH` 的标量参数，都会直接报错 |
| `SWITCH` | 按名字返回对应的度量值 | — |
| `ERROR(...)` | 兜底：没选中或多选时给出明确报错 | 静默返回空白，用户以为"没数据"，其实只是没选指标 |

**为什么必须有 `SELECTEDVALUE`**：度量值在高聚合的上下文里求值，DAX 无法确定该取哪一行的列值，所以"直接写 `Metric[Measure]`"在语法上就不成立。这一层"安全读取用户选择"的包装，正是参数表模式能成立的前提。

### 累计分布（帕累托）不要用分类轴

帕累托分析要回答"多少比例的客户贡献了 80% 的金额"。**用客户名当分类轴会失效**：

| 场景 | 分类轴上的表现 |
| --- | --- |
| 单个国家、客户数少 | 勉强可读 |
| 单个国家、客户数多 | 只能看到少数客户，必须加滚动条 |
| 多国对比 | 折线不跨国家连接，图基本没用 |

改法是**换一根连续数字轴**（第 1 名、第 2 名……第 N 名），每个位置显示"前 N 名客户的累计值"。这样累积线才是连续曲线，也才可能把不同国家的分布放在同一张图里比较。

两点实现要点：

1. 轴表是一张**计算表**，用 `GENERATESERIES` 之类生成 1…客户数的整数序列，放进模型但**不与任何表建立关系**——它只提供坐标，不提供筛选（见 [[Power BI 分析与建模]] 10.2）。
2. 各国客户数不同，横轴的"第 N 名"含义也随之不同；比较时要说明这点，或改用百分位。

> **来源**：这一做法（包括参数表模式）源出自 **SQLBI** 的文章，不是《Power BI 疑难解答》——来源材料把它标错了。
> **已实测**：上面那段 `Metric Value` 与真实模型里的定义一致，行为已逐条核对——
> - 不选指标时 `SELECTEDVALUE(Metric[Measure])` 返回空，`SWITCH` 落到 `ERROR` 分支，报出「Measure not selected in Metric[Measure]」，**没有静默返回空白**；
> - 选中 `Total Cost` 时该度量值返回 3,208,213.91，而并列对照的直接 `[Sales Amount]` 仍是 7,305,939.03，说明切换确实换了度量值；
> - 累计是否到 100% 也验过：在一个 3,157 名客户的集合上，`Pareto %` 的最大值为 **1.0**。

## 性能：先测瓶颈，再改模型

“图太多”“DAX 太慢”是可能原因，不是诊断。先用 Power BI Desktop 的 **Performance Analyzer** 记录慢页面，区分 DAX 查询、视觉渲染与其他耗时，再选择改进：

1. 查询慢：检查事实表粒度、关系、度量值和筛选条件；必要时回到数据源或模型层预聚合。
2. 渲染慢：减少同页重复视觉对象或昂贵交互，确认所选视觉对象适合数据量。
3. 刷新慢：单独检查 Power Query 转换、数据源和刷新策略；不要用报表页面优化去解决数据加载问题。

每次只改一类因素，保留前后相同筛选条件下的测量记录。隐藏视觉对象、换成 SVG 背景或减少 DAX 公式都不保证性能提升，必须实测。

**写度量值时就已经在决定性能**：能写成布尔筛选器的条件不要包一层 `FILTER`，能放在 [[Power Query 数据处理]] 完成的派生列不要留给 DAX 计算列——这两条比事后调视觉对象更有效。

## 现阶段认知

报表质量＝**口径正确、问题可回答、用户能操作、性能可量化**。

前两项归 [[Power BI 分析与建模]]，第三项是本节的设计部分，第四项必须靠测量而不是靠感觉。视觉对象的选择只是最外层——数字不可信时，交互设计做得再好也没有意义。
