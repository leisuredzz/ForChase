# AI应用概念关系

> **核验状态**：未核验——概念关系为整理时撰写，随产品与版本变化，尚无来源标注与可复现的记录。详见 [[知识库质量审计]]。

这篇笔记从初学者视角解释 Model、API、Prompt、Context、Tool、RAG、Agent、Memory 和 Workflow 如何组合成一个能够实际工作的 AI 应用。

## 背景：模型只是发动机，不是整辆汽车

人们常把大语言模型称为“AI 的大脑”。
这个比喻有帮助，但也容易让人误以为只要有模型，就自然拥有文件读写、联网、记忆和自动执行能力。

更准确的类比是：

- Model 是发动机；
- Prompt 是驾驶指令；
- Context 是当前地图和车内资料；
- Tool 是方向盘、轮胎和机械臂；
- Memory 是行车记录和档案；
- RAG 是出发前查地图和资料；
- Workflow 是规定好的行驶路线；
- Agent 是根据目标不断观察和选择动作的驾驶系统；
- AI 应用是把所有部件装配起来的整辆汽车。

因此，同一个模型放在不同应用中，表现可以非常不同。
差异可能来自提示、上下文、工具、检索资料、权限和工作流程，而不一定来自模型本身。

## 一张完整关系图

~~~mermaid
flowchart TD
    U[用户目标] --> A[AI 应用]
    A --> P[Prompt 提示]
    A --> C[Context 上下文]

    A --> T[Tools 工具]
    A --> W[Workflow 工作流]
    A --> MEM[Memory 记忆]
    P --> M
    C --> M
    R --> C
    M --> A
    A --> T
    T --> A
    MEM --> C
    W --> A
    A --> O[结果与外部动作]
~~~

## Model：负责生成和判断

### 模型是什么

大语言模型通过大量文本和其他数据训练，学习输入与输出之间的统计关系。

当模型接收到文字时，它会把文字切分为 Token，再根据已有输入预测后续 Token。
连续预测形成句子、代码或结构化结果。

可以把模型想象成读过大量资料、非常擅长续写和归纳的工作人员。
它并不是从数据库中逐句抄出答案，而是在当前输入和训练所得参数的共同作用下生成输出。

### Token 是什么

Token 是模型处理文本的基本单位。
它可能是一个字、词的一部分、标点或代码片段。

Token 数量影响：

- 上下文能放多少内容；
- 请求的计算量；
- 响应速度；
- 费用；
- 长文中信息是否会被截断。

字符数、字数和 Token 数不是同一个概念。

### 训练与推理

训练是让模型从大量样本中调整内部参数。
它像长期教育过程，成本较高，不会因为一次普通对话就实时改写所有模型参数。

推理是已经训练好的模型接收本次输入并生成输出。
日常聊天、代码生成和摘要通常属于推理。

### 模型知道什么

模型的输出可能来自：

- 训练阶段学到的一般模式；
- 当前 Prompt；
- 当前上下文；
- 应用检索到的外部资料；
- 工具返回的结果。

如果应用没有提供最新信息，模型未必知道刚刚发生的事情。
语言流畅也不等于事实正确。

## Prompt：告诉模型要做什么

Prompt 不只是一个问题，它可以包含：

- 角色；
- 任务；
- 背景；
- 输入数据；
- 约束；
- 输出格式；
- 示例；
- 判断标准。

一个模糊 Prompt：

> 分析销售数据。

一个更清楚的 Prompt：

> 根据给定订单明细，按店铺和月份计算净销售额。净销售额等于商品金额减折扣和已完成退款。先检查币种是否一致，再输出汇总表和异常记录。

后者明确了数据范围、计算口径、检查动作和输出形式。

Prompt 像给同事布置任务。
“把这个处理一下”容易产生分歧；目标、材料和验收标准越清楚，结果通常越稳定。

## Context：模型本次能看到的现场

Context 包括本次请求中提供给模型的所有信息，例如：

- 当前问题；
- 对话历史；
- 文件内容；
- 系统规则；
- 检索资料；
- 工具结果；
- 示例；
- 中间步骤。

模型不会自动看到你的整个电脑、公司数据库或所有历史对话。
应用必须选择并提供相关信息。

### Context Window

上下文窗口是模型单次处理信息的容量范围。

可以把它想象成办公桌：

- 训练所得能力像工作人员长期掌握的知识；
- 上下文像当前摆在桌面上的材料；
- 桌面有限，材料过多会需要筛选、压缩或分批处理。

上下文越长不一定越好。
无关材料会增加噪声，也可能掩盖真正重要的信息。

## API 与 SDK：程序怎样使用模型

### API

API 是应用程序接口。
它像服务窗口：调用方按照规定格式提交请求，服务方按照约定返回结果。

一个模型 API 请求通常包含：

- 使用哪个模型；
- 输入消息；
- 输出长度；
- 是否允许工具；
- 结构化输出约束；
- 其他生成参数。

API 不是模型本身。
它是程序访问模型能力的通道。

### SDK

SDK 是软件开发工具包。
它把底层 HTTP 请求、鉴权、数据结构和错误处理封装成更方便的代码接口。

类比餐厅：

- API 是后厨规定的点餐协议；
- SDK 是服务员和点餐系统；
- Model 是后厨的烹饪能力。

不用 SDK 也可以直接调用 API，但需要自己处理更多技术细节。

## Structured Output：让结果可以被程序使用

人可以理解自由文本，程序更喜欢稳定结构。

例如程序需要：

~~~json
{
  "sku": "A001",
  "risk_level": "high",
  "reason": "库存低于安全线"
}
~~~

而不是每次获得风格不同的一段说明。

结构化输出通过 Schema、字段类型和枚举值约束结果，使下游程序更容易验证和处理。

即使使用结构化输出，程序仍应检查：

- 字段是否缺失；
- 类型是否正确；
- 数值是否越界；
- 业务规则是否满足；
- 结果是否需要人工审批。

格式正确不等于内容正确。

## Tool：给模型连接外部能力

模型擅长理解和生成，但通常不能仅凭自身完成所有外部操作。

工具可以提供：

- 网页搜索；
- 数据库查询；
- 计算器；
- 文件读写；
- 代码执行；
- 日历和邮件；
- 企业系统接口。

工具像员工可以使用的设备。
模型可以提出“需要查库存表”，应用再决定是否允许并真正执行查询。

### Function Calling

Function Calling 让模型按照预定义结构提出工具调用。

流程通常是：

~~~text
用户：查询 A001 的库存
    ↓
模型：需要调用库存查询工具，参数 sku=A001
    ↓
应用：检查权限并执行
    ↓
工具：返回 US=100，UK=30
    ↓
模型：解释查询结果
~~~

模型提出调用不等于工具已经执行。
真正的权限控制、参数校验和执行通常由应用负责。

### 工具使用的风险

只读搜索和发送邮件的风险不同。

应用需要区分：

- 只读与写入；
- 可逆与不可逆；
- 普通数据与敏感数据；
- 单次操作与批量操作；
- 自动执行与人工确认。

让模型拥有工具，等于给员工发放权限。
不能只关注员工聪不聪明，还要设计门禁和审批。

## RAG：先查资料，再回答

RAG 是 Retrieval-Augmented Generation，即检索增强生成。

基本流程：

1. 用户提出问题。
2. 系统把问题转成检索条件或向量。
3. 从知识库中找出相关片段。
4. 把片段放进上下文。
5. 模型根据问题和片段生成答案。

### 为什么需要 RAG

模型参数不适合频繁保存企业最新制度、产品说明和每天变化的数据。

RAG 像开卷考试：

- 模型提供阅读、理解和表达能力；
- 知识库提供当前资料；
- 检索负责把相关页面翻到桌面上。

### RAG 的关键环节

- 文档采集：资料是否完整。
- 切分：一个片段多大，是否破坏上下文。
- 表示：怎样把问题和文档转换成可比较形式。
- 检索：怎样找到真正相关的片段。
- 排序：怎样把更有用的结果放在前面。
- 生成：怎样要求模型依据资料回答。
- 引用：怎样让使用者追溯依据。
- 评估：检索和回答是否真的正确。

### RAG 不能自动保证正确

如果知识库内容错误、检索漏掉关键条款或模型错误理解，最终答案仍可能出错。

因此要分别评估：

- 相关资料是否被检索出来；
- 检索资料是否支持最终结论；
- 答案是否忠于资料；
- 没有答案时系统是否承认不知道。

## Memory：让应用延续状态

Memory 通常由应用保存，而不是模型天然永久记住。

它可以分为：

- 短期记忆：当前任务的最近步骤和中间结果。
- 长期记忆：用户偏好、项目背景和过去结论。
- 情节记忆：发生过哪些任务和操作。
- 语义记忆：提炼后的事实和知识。

记忆不是保存得越多越好。

需要考虑：

- 什么值得保存；
- 谁可以读取；
- 多久过期；
- 如何更新过时内容；
- 用户能否查看和删除；
- 错误记忆如何纠正。

把所有对话原文永久塞入上下文，会造成成本、隐私和噪声问题。
更好的方式通常是保留必要事实，并在需要时检索。

## Agent：围绕目标循环行动

Agent 可以理解为一种运行模式：模型围绕目标观察当前状态、选择动作、接收结果，再决定下一步。

~~~mermaid
flowchart LR
    G[目标] --> O[观察状态]
    O --> D[决定下一步]
    D --> A[调用工具或生成内容]
    A --> R[读取结果]
    R --> O
    R --> E[满足终止条件]
~~~

例如“整理一个文件夹”可能需要：

1. 列出文件；
2. 阅读内容；
3. 判断分类；
4. 建立目录；
5. 移动文件；
6. 检查链接；
7. 发现错误后修正。

这不是一次生成就能稳定完成的任务，而是多步循环。

### Agent 需要的边界

- 明确目标；
- 可用工具；
- 权限范围；
- 最大步骤或成本；
- 失败重试；
- 停止条件；
- 人工确认点；
- 日志和审计；
- 结果验证。

没有边界的 Agent 像一名任务模糊、权限无限、没有预算和验收的员工。

## Workflow：把可靠步骤固定下来

Workflow 是预先设计的步骤和条件。

例如报销审核：

~~~text
读取票据
→ 提取字段
→ 校验金额
→ 检查预算
→ 超过阈值交人工审批
→ 写入财务系统
~~~

Workflow 的优点是可预测、易测试、易审计。
Agent 的优点是能处理不确定和开放问题。

成熟系统经常结合两者：

- 固定流程由 Workflow 控制；
- 文本理解和例外判断交给 Model；
- 开放探索环节使用 Agent；
- 高风险动作保留人工审批。

## Agent Framework：开发时的脚手架

Agent Framework 帮助开发者管理：

- 消息和状态；
- 模型调用；
- 工具注册；
- 工作流；
- 记忆；
- 重试；
- 追踪；
- 评估。

框架像建筑脚手架，能提高施工效率，但不会替你决定建筑用途和结构。

选择框架前应先明确问题。
一个简单的模型调用不需要为了“更智能”而强行加入复杂 Agent 架构。

## Fine-tuning：调整模型行为

微调通过特定训练数据调整模型的行为。

它适合：

- 稳定的输出风格；
- 特定格式；
- 重复任务模式；
- 领域行为适配。

它通常不适合用来保存每天变化的库存、制度或新闻。
这类知识更适合数据库、工具或 RAG。

可以这样区分：

| 需求 | 更常见的方法 |
| --- | --- |
| 告诉模型本次任务 | Prompt |
| 提供本次文件 | Context |
| 查询最新企业资料 | RAG 或 Tool |
| 保存用户偏好 | Memory |
| 执行外部操作 | Tool |
| 约束固定步骤 | Workflow |
| 调整稳定行为模式 | Fine-tuning |

## 评估：不能只看回答像不像

AI 输出很自然，因此人容易高估其正确性。

评估需要把任务拆开：

- 事实正确性；
- 是否完整；
- 是否遵守格式；
- 是否引用正确资料；
- 工具参数是否正确；
- 是否执行了不该执行的动作；
- 在不同输入下是否稳定；
- 成本和延迟是否可接受。

对于数据分析任务，还要检查：

- 计算是否正确；
- SQL 是否重复计数；
- 单位和币种是否一致；
- 缺失值如何处理；
- 结论是否超出数据支持范围。

## 一个企业知识助手案例

假设要建设“产品制度问答助手”。

它可能包含：

~~~text
用户问题
   ↓
权限检查
   ↓
从制度库检索相关段落
   ↓
模型生成回答并附引用
   ↓
若需查询具体 SKU，则调用主数据工具
   ↓
对写入或修改请求进行人工确认
~~~

各部件职责：

- Model：理解问题并组织回答。
- RAG：找到最新制度。
- Tool：查询实际产品数据。
- Memory：记住当前会话讨论的产品。
- Workflow：固定权限和审批步骤。
- Agent：处理需要多步查询的复杂问题。

## 常见误区

- 模型等于完整 AI 应用。
- 上下文越长越好。
- RAG 能消除幻觉。
- Agent 一定比固定流程先进。
- 模型请求工具就代表工具已经执行。
- Memory 等于永久保存所有对话。
- 微调适合灌入最新事实。
- 输出是 JSON 就代表内容可靠。
- 模型更大就必然更适合所有任务。

## 现阶段认知

理解 AI 应用时，可以依次问：

1. 谁负责生成和判断？
2. 模型本次看到了哪些上下文？
3. 最新事实从哪里检索？
4. 哪些能力由外部工具提供？
5. 谁真正执行操作并检查权限？
6. 状态和记忆保存在什么地方？
7. 哪些步骤固定，哪些步骤允许模型选择？
8. 何时停止，怎样验证结果？

当这些问题被拆开后，Model、RAG、Tool、Memory、Agent 和 Workflow 就不再是一堆流行词，而是一套各司其职的系统部件。
